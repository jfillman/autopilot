## What it is

One static binary, `autopilot-gateway`, on distroless static (nonroot, uid 65532, no shell: the same bases as
Clearance's image, `gateway/Dockerfile`):

| Subcommand | Does |
|---|---|
| `serve` | the MCP server (`PORT`, default 8080) with the person-facing routes beside it (`/v1/...`, S3), the model proxy (`MODEL_PORT`, default 8081, only with `MODEL_KEY_FILE`), the expiry sweep (close, delete runs, backstop outcomes) and the outbox drain, and, when asked, the interval scheduler (`SCHEDULES_ENABLED`), the event bridge (`EVENTS_ENABLED`) and the reconciliation sweep |
| `conformance-control` | the test-only conformance control interface; off unless `GATEWAY_CONFORMANCE_CONTROL=1`, loopback only |
| `api` | **not ported**: exits 2 and says so. The read API is still the Python `autopilot-gateway api` |
| `version` | the image's version (`AUTOPILOT_GATEWAY_VERSION`, else the build's) |

It is built on:

- **MCP**: the official Go SDK (`github.com/modelcontextprotocol/go-sdk` v1.8.0): streamable HTTP, stateless, JSON
  responses, a bearer token verified before any tool runs (401 otherwise), protected-resource metadata, `GET /healthz`.
  The tools it carries keep their Python names and result shapes: `tools_list`, `agents_list`, `session_open`, `call`, and
  (S2) `run_finish` and `session_close`; `run.spawn` and `run.close` are tools inside a session (`call`).
- **Clearance**: the Go client Clearance ships (`github.com/jfillman/clearance/client`, R-1e), pinned to the same
  release as the Python client and the test core (`CLEARANCE_REF` in `.github/workflows/test.yaml`, `pyproject.toml`,
  `gateway/go.mod`; bump the three together: `tests/test_gateway_go.py` fails when they differ). Autopilot's code reaches
  Clearance only through this API. The decision path asks for an answer within 1 s per attempt (`CLEARANCE_CORE_TIMEOUT`,
  0.05 to 30; the Clearance client's own default of 250 ms was shorter than a ledger append that took 306 ms live),
  retries a timeout, a connection failure or a 503 once, and opens its breaker after 5 consecutive failures.
- **The model proxy**: a streaming reverse proxy. A response body is relayed chunk by chunk with a flush and is never
  held: the first server-sent event reaches the run while the provider is still producing the rest. Usage is metered
  from the events as they pass (or from a bounded copy of a plain answer) and charged when the call ends, however it
  ends; every allowed call gets exactly one outcome (`ok`, `error:Upstream<status>`, `error:StreamInterrupted`, ...).
- **The gateway database**: the same tables, columns and writer lock as the Python gateway
  ([gateway-database.md](gateway-database.md)). `gateway/internal/pgstate/schema.sql` is generated from the Python
  `SCHEMA`; a session row either implementation wrote loads in the other. Sessions are saved durably after every
  operation, with concurrent saves grouped into one transaction.

Tool names, tiers, arguments, costs and the baseline deny lists are the Python registry's
(`gateway/internal/tools/registry.json`, generated by `tools/gen_gateway_registry.py`; `tests/test_gateway_go.py` fails
when it is stale). The bundled agent definitions parse to the same scope and agent the Python parser sends the core.
The same generator writes three more fixtures from the Python code, so a Go test can hold the Go result equal to the
Python one: session rows as `Session.to_record` writes them (`session/testdata/rows.json`, read and written back whole),
what the agent is told and the outcome records for each kind of backend failure (`dispatch/testdata/backend_errors.json`)
and the effect a write's outcome carries (`dispatch/testdata/effects.json`).

### The run's identity, in plain words

A caller acts as a session only when it IS that session's run. The gateway decides that from four things, all of which it
holds itself: the session has a run (a name the gateway wrote when it created the run, never taken from a caller), the caller
is a workload token that the Kubernetes token review verified, the caller's verified identity (`namespace/serviceaccount`)
is exactly `agent-<run>/run` for that run, a name of `r-` and 6 to 32 hex digits, and (S3, [the pod binding](#the-pod-binding-a-9-s3))
the token is bound to the run's pod. Then the gateway tells the core "this caller
acts as the session's principal", and the core decides as it would for the person. Nothing the caller sends is read: not an
argument, a header, a label or a name.

So these all act as themselves and are refused by the core as another principal's session (R001): a sibling run, a child
acting as its parent, a parent acting as its child, a run in another namespace with the same service account name, the run's
own namespace with another service account, a person whose id looks like a run's, a run of a session with no run (finished or
deleted), and a replayed token after `run.close`. Each is a test (`TestARunActsOnlyAsItsOwnSession`,
`TestAReplayedRunTokenActsAsNothingAfterItsRunIsGone`, `TestAClosedSessionWhoseRunWasNotDeletedStillAllowsNothing`).

Stricter than Python, deliberately: the caller must be a `workload` (Python only compares ids), the run's name must be a
real run name, and the token must be bound to the run's pod. `acting.json` records Python's answer and Go's for each case; the two differ only for a user whose id is a run's
and for a run name no run has.

### What is deliberately not the same as Python

All of these leave the answer for ordinary inputs unchanged.

- **The gateway checks the core's spawn grant.** The core cuts a child's limits; Python adopts the grant as it is. Go also
  refuses it (R007, nothing created, one refused outcome) when it is wider than the definition's limits cut to what the parent
  has left, names another principal, task or agent than the parent's, reuses a session id, goes deeper than 3, outlives the
  parent, or reserves other than the child's limits. Budget, depth, fan-out, tools, models, tier, network and compute can only
  narrow from parent to child even if the core would allow more. Every grant the real core made in the replay corpus passes.
- **A spawn's check and reservation are one step under the parent's lock** (`Store.AdoptChild`), and one session's calls are
  serialized, so concurrent spawns cannot overspend a parent, even while the model proxy charges it. The storm tests run with
  `-race`.
- **Write-ahead of the run's name.** A run's name is saved with its session (and a spawn's reservation with the parent) before
  the run is created; Python keeps everything in memory until the operation ends. See the crash points.
- **A run that fails to be created is deleted again**, best effort, because a timeout can come after the API server took it.
  Python leaves it to its own deadline. A spawn whose call ran out of time after the run was made is undone too.
- **A session launches once.** A second `launch` of a session with a run is refused (R001); Python tries to create it again
  and gets the API server's 409.
- **A spawn's `input`** must be an object that fits the AgentRun's 4 KiB, and every label value in the manifest must be a
  valid Kubernetes label value: refused (R008, or `RunRefused` before any request) rather than left to the API server.
- **`run.close` with a `run_id` that is not a string** is refused R001; Python raises a TypeError.
- **A grant's parent must be the session that asked.** The check that the grant's parent is the calling session is Go's only;
  Python looks the parent up by the grant.
- **The sweep is bounded, which Python's is not.** Python retries a run whose delete keeps failing on every sweep, forever, and
  writes a `run.delete error:` record each time, and a run named by an ancestor and by its own entry is attempted again in the
  same sweep. Go retries on a backoff (1, 2, 4 ... capped at 30 minutes), records a failure when it starts and then at most
  once an hour while it keeps failing, records the success once, and handles each run at most once per sweep. A close by a
  person or a run always tries at once.
- **The failure state of a delete that keeps failing is saved with the session** (a `delete_failure` key inside the session's
  JSON document: attempts, first failure, last record, next try), so a restart continues the backoff and the hourly record
  limit instead of retrying everything at once. No schema change. The Python gateway reads a row by the keys it knows, so it
  ignores the key; its next save of that session writes the row without it and the backoff starts again. The first failure and
  each hourly record are also logged at error level, naming the run, the session, the error kind and the attempts. A person's
  or a run's own close always records its own result. The sweep's log line counts the sessions it actually tried, not those
  waiting out a backoff.
- **A session closed while its run is being created** (a person's End, the parent's close, the sweep) has the run deleted
  afterwards and the agent told, with the refund made once by the close; Python would leave a live run. A launch whose
  `run.launch` record cannot be written, and whose delete fails too, keeps the run's name so the sweep retries the delete.
- **`run_finish` checks again, under the session's lock, just before it sets the outcome**: a finish that lost to the deadline
  or the sweep's `expired` takes back the answer it stored and is refused R004.
- **The sweep's reads rotate** (each sweep starts after the last session the previous one reached) and its wait for them has a
  deadline of its own, so a mostly hung API server starves no session and a backend that ignores its context cannot hang it.
- **The sweep has one deadline and holds no session lock across the API server.** Closing the sessions past their deadline
  comes first and needs no API server; the reads of how runs ended run a few at a time (8) within the sweep's deadline, with
  no session lock held, and are applied only to a session that is idle (an operation in flight is looked at on the next sweep)
  and unchanged since the read. A child whose run is being made holds its operation lock until the run exists (parent first,
  then child, the only order), and its run epoch changes when the run is made, so the sweep cannot mistake the API server's
  404 for a run that does not exist yet for a run that is gone. Python reads each run in turn under the session lock.
- **`run_finish` for a session that is not the caller's run is always R001**, unknown, closed or another's alike, so the answer
  does not say whether a session id exists (Python answers an unknown or closed one R004 first). Its own run, after the session
  ended, is still told R004. A finish at or after the session's deadline, or after the sweep wrote `expired`, is refused R004
  and cannot overwrite that outcome; Python accepts it.
- **A spawn whose time ran out while its child was being saved** is undone or succeeds, never both: the answer is not turned
  into a timeout after the child's fate is decided.
- **A run's answer is saved before its session closes**, in two transactions (Python: one). A crash between leaves the session
  open and the run finishes again; the first answer is the one kept.

### Crash points

What the database holds if the process dies at each point, and what the next gateway does. The sessions are saved at each
step marked (save).

| Dies | Database holds | Next gateway |
|---|---|---|
| in a spawn, after the core's decision, before the child exists | nothing new (the core has the allow record) | nothing: an unused session id, no run, no reservation. Python the same |
| after the child exists in memory, before its save | nothing new | the same |
| after the write-ahead save, before the run is created (save) | the child, live, naming its run; the parent's reservation and the call's charge | the run does not exist, so no pod holds the child's identity. The sweep closes the child at its deadline, deletes the run it names (a 404 is success, recorded `deleted`), and the reservation comes back. Python: the state is lost whole, nothing to clean |
| after the run is created, before the call ends | the same row; the run exists | the child's pod can call (its session is known, so it is decided and recorded); the sweep deletes it at the deadline or when the session closes. Python: the pod's session is unknown to the restarted gateway, so every call is refused, and the AgentRun is left to its own deadline (the composition enforces it without the gateway) |
| a launch, after the write-ahead save, before or after the run exists (save) | the session naming its run | the same sweep |
| a launch's `run.launch` record cannot be written (core down) | the run was created; the record was required | the run is deleted again, the session names none (fail closed, as Python) |
| a finish, after the answer is kept, before the session closes | the answer; the session open | the run finishes again; the first answer stays |
| a close, after the session closes in memory, before its save | the session still live | the person or run closes it again; its budget was never returned in the saved rows |
| the run's delete fails | the session closed, still naming its run | every sweep retries and records each attempt (`error:KubeRunError`, then `deleted`) |

What a crash cannot undo: the evidence records the gateway wrote before it died (the core has them), and a run the API server
took after the gateway lost its connection to it.

### The namespace assumption behind run identity

The rule above rests on one fact outside the gateway: nobody but Crossplane (the AgentRun composition) can create a namespace
named `agent-r-<hex>` or a service account `run` in one. A principal with namespace-create, or with create on serviceaccounts and
tokens in such a namespace, could mint a token that passes the token review as a run and act as that run's session. So the
gateway's RBAC, the chart and the cluster's admission policy must keep namespace creation for `agent-*` names with the
composition's identity, and nobody else may hold `create` on namespaces. The gateway does not read Kubernetes on the hot path to
check it.

### The pod binding (A-9 S3)

The identity above is a namespace and a service account, and a token for the bare service account is that identity. Anyone who may
create tokens for `agent-<run>/run` (the TokenRequest API) can mint one, bound to no object or to any other. So a caller acts as a run
only if its token is also **bound to the run's pod**: the token review's `status.user.extra` carries the bound pod's name under
`authentication.kubernetes.io/pod-name` (and its uid, and the node's name and uid, and a credential id), and `auth.Workload` puts that
name on the principal (`Principal.Pod`). `Gateway.Acting` then requires it to be `agent`, the name the composition gives a run's pod.

What this relies on, stated plainly:

- **Kubernetes** ("Bound service account tokens", service accounts admin guide, read through the documentation tool on 2026-11-14): a token
  bound to a Pod carries the pod's `metadata.name` and `metadata.uid` as private claims; the API server's service-account authenticator
  verifies them (and that the pod still exists) and returns them as the `authentication.kubernetes.io/pod-name` and `/pod-uid` extras of a
  token review. The node name and uid in the JWT are not verified by the API server and are not read here. A token bound to a Secret or a
  Node, or to nothing, has no pod-name extra.
- **The pod's name** is not set by the composition directly. The composition (`vendor/agentrun_compose.py`, `SANDBOX_NAME`) creates one
  Sandbox named `agent` per run, with no warm pool and no claim, and the agent-sandbox controller names the pod after its Sandbox (its
  documentation: "the backing pod name matches the sandbox name", with a Sandbox `agent` and a pod `agent` in its network-policy example). So
  the rule holds as long as the composition and the controller keep that naming. `TestPodNameIsTheCompositionsSandbox` fails if the vendored
  composition renames the Sandbox; a controller that changed its naming would show as every run being refused (fail closed), which a live
  check on a deployed cluster would catch (owed, as everything that needs a cluster is).
- A missing key is **not** a failure of ordinary authentication: a workload token without a pod binding still authenticates (the run's
  own gateway-side checks, Tower's backend and every other workload do not need one); it simply cannot act as a run. Several values, an empty
  one or a name that is not a DNS name count as no binding.

Tests (`TestARunActsOnlyWithATokenBoundToItsPod`, `TestTheBoundPodIsCarriedOnTheWorkloadPrincipal`): the right pod; the right identity with
another pod name, with a suffixed one, and with none; a foreign-cluster principal that carries the run's identity and a pod name; a person
(with and without a pod); another run's pod; and the same rule for `run_finish`, `session_close` and `session_tools`.

### Who may do what

Person controls are for people. The rule is Python's (`control.py`, `Gateway._person`, `_manager`), with nothing looser:

- **Who is a person.** A caller whose kind is `user` (their own sign-in), or a *delegate* naming one: a caller whose id matches a glob of
  `AUTOPILOT_DELEGATES` and who sends `X-Hangar-On-Behalf-Of: user:<name>`. Nothing else is: a run, a service account that is not
  a listed delegate, Tower's backend with no name or a bad one, and every other cluster's workload are refused (`HR-PERSON` 403, or
  `HR-DELEGATE` 403 when they name someone); a non-delegate that sends the header is refused, not ignored. A delegate is named by where
  it runs: the list is refused at start if an entry is `*`, starts with a wildcard, or has a wildcard in its namespace (or cluster):
  `namespace/name` for this cluster, `cluster/namespace/name` for another, every segment but the name literal. A glob never crosses a
  `/` (the match is segment by segment), another cluster's principal needs a three-segment glob, a run (`agent-<run>/run`) is never a
  delegate even if a glob would match it, and a person-kind caller is never one. The name in the header is `user:<name>` of at most 200
  bytes, valid UTF-8, with no control character (a tab, ESC, newline), no format character (a zero-width or direction mark) and no
  U+2028 or U+2029; a request that carries the header more than once is refused. Python takes any glob and any string. A run is a workload that is not in the delegates list (the list is the deployment's), so
  **a run can never answer its own `human.request`, release its own hold, freeze, end or run anything, and has no way to raise its
  own budget** (a run's budget is cut by the core at open; nothing in this slice changes one).
- **Who may act on what.** The agent's owner group (the definition's `owner`, resolved by a Directory), a platform admin
  (`AUTOPILOT_ADMINS`, globs), and, for a session only, the person whose session it is. Holds, releases, a run and a Preflight score are
  the agent's, so the session's person alone is not enough for them. Answering an inbox request is its owner's (the session's person)
  and the agent's owner group: an admin is not an answerer.
- **Without a Directory** only the session's own person and the admins act. The Go gateway has no Directory yet: S5a brought the catalog
  client, but the group lookup (`BackstageDirectory`) is not wired, so an owner group is not resolved until then.
- **`human.request.get` is bound to the asking session's task, not to the session**: a child or a sibling session of the same run tree
  (they share the task) can read the question and the answer of a request any of them asked, as in Python. The request is the session's
  owner's to answer, and the owner group's; the run tree is one person's.
- Each control is an evidence record naming the person and the delegate. A refused call writes nothing and changes nothing.

Each of these is a test (`TestPersonControlsAreForPeopleOnly`: 6 controls against 19 callers, each either allowed by the rule or
refused with no record and no change; `TestWhoIsAPerson`; `TestThePeopleRoutes`, which sends a run's token to every route with
and without an on-behalf-of header; `TestAnUnauthenticatedCallerLearnsNothing`): another person, a workload, a run bound to its
pod, a service account bound to no pod, a foreign-cluster principal that is not a delegate, a delegate naming nobody, a delegate
naming a person who may not, an unlisted workload naming an admin, a person whose id looks like a run's, and a person naming
someone on behalf.

### The trigger rule

No trigger source is trusted to choose the principal, the agent, the budget or the tools. The agent is the one whose definition's
trigger matched. The core decides the open as `trigger:<name>` (a workload at tier 1) and cuts the limits from the definition. The
gateway then checks the grant itself (`checkOpenGrant`): for the agent asked, no parent, depth 0, the definition's own service
account as the principal when it names one, no limit, tool, model, tier, network or compute above the definition's, a deadline no
later than the definition's ttl, the session id the gateway named, the task it sent. Anything else is refused (`CORE-REFUSED`) and
nothing is created. A dedupe is accepted only for the live session the gateway itself showed the core. A person's run gets the same
check against the person. An event is untrusted input: its id, routing key, app, received time and subject id have the forms and
lengths glidepath-api gives them (an id is `[A-Za-z0-9:._/@+=-]` and at most 200 characters; the others at most 256), its `event` is
an object, and it is dropped and counted (`oversize`, `malformed`, `bad-id`, `bad-key`) otherwise. What reaches a run is a summary
of it, never the event.

A triggered session's principal is the definition's service account (the core: `d.ServiceAccount`, or "" when it names none; the replay corpus's
31 triggered opens all carry it). The schema requires a service account of a workload definition. S3 did not validate definitions, so a workload definition without one is refused **up front**
(R008, "no service account", the core is not asked): there is no identity a triggered run could have, and the dedupe rule (compare with that principal) could never
accept it. S4 validates every definition and the refusal stays: a document with no service account for a workload identity is refused by the schema, so no loaded
definition can reach it (`TestAParsedWorkloadDefinitionAlwaysHasAServiceAccount`, over the corpus, and the fuzzers); it remains as the second line for a definition built by hand.

### The event bridge as a network client

It has an HTTP client of its own (10 s to connect, 10 s for TLS, 30 s for the answer's headers, 60 s for a JSON read), follows no
redirect (the gateway's token travels in two headers, and a redirect is the one way it could reach another host), reads at most 8 MiB
of a JSON answer, at most 64 KiB of a stream line and 256 KiB of one event (a larger one is dropped, the stream goes on), drops a stream
that is silent for 90 s (pings count), reconnects after 5 s doubling to 60 s with jitter (a stream that delivered or stayed up 30 s starts
it over), and names no token or URL in an error or a log line. It runs on goroutines of its own, handles one event at a time, gives each
event 2 minutes at most, and every call into the gateway has its context, so it cannot stall a tool call. The cursor follows only ids of
the form glidepath-api's are (16 digits of receive time in microseconds, a dash, a hash) that are not in the future, and never moves
backward; a ledger failure ends the stream and leaves the cursor at the last event that was fully handled, so the resume sees the failed
one again.

### Crash points of the triggers

What the database holds if the process dies at each point, and what the next gateway does. A trigger is one row, `(agent, key)`, claimed
before anything opens and decided after.

**The rule.** Handling in one process is serialized and the gateway is the only writer of its database (the writer lock), so when a claim is
taken no other claim is in flight: a row that is still `claimed` is an orphan (a crash, or a write that gave up), never a live handling, and
the claim is taken over at once (a cut-off of "now"; Python's five minutes are gone). A delivery is reported `deduped` only when the row is
**decided**. The session is written to the row (`Ledger.Opened`) right after the open and before the launch, and kept when the claim is taken
over.

What a takeover does depends on **facts the session recorded**, never on the clock or on a field's absence. The session records, each in its
own durable write at the moment it happens: its `run` name (reserved before the run is created); `launched_at` (the run was created, its own
write right after); `close_reason` (`control`, `by`, `at`: written in the same step as the close: `end` by a person, `deadline` by the sweep,
`abandon`, `unrecorded`, `close`, `parent`, `finish`, `other`); and `run_removed` (`reason`, `at`: `hold`, `closed`, `record-failed`: written
before a run is deleted). A takeover reads those, and the backend, and nothing else:

- **removed** (`run_removed`): a marker is not a deletion. The takeover closes the session (recorded reason), deletes the run, and confirms
  through the backend (a GET by name: 404) that it is gone; only then is the row decided from the reason (`hold` is `held`, `record-failed` is
  `launch-failed`, `closed` is `refused`). A delete that fails, or a GET that cannot answer, leaves the key resumable, never decided;
- **closed with a run named**: the backend is asked. A run that is there is deleted and its absence confirmed before anything is decided
  (a closed session leaves no live run); an answer that cannot be had is resumable. Then: `launched_at` recorded or a run that was there and
  a recorded `deadline` is `launched`; frozen is `refused`/`CT-FROZEN`; a person's end is `refused`/`CT-ENDED`; any other reason, or none
  recorded, is `refused`/`CT-CLOSED` (never launched, never reopened); a recorded `deadline` or `unrecorded` with no run is replaced by a
  fresh session while the trigger is valid (an event: 24 hours; a slot: its 10 minutes of grace), else `missed`;
- **live**: launched. A hold is read immediately before **every** create, a resumed one included, and the session's own state (closed,
  frozen) again with it; a hold read again after the run exists takes the run away (marker first). A frozen live session keeps the run it
  has and makes none; a session ended in the same window is closed (above);
- a **create** is classified: a 409 on the session's own reserved name (unique to it) is the run, made by an attempt whose answer was lost;
  a refusal that proves nothing was made (a 4xx) releases the name and is `launch-failed`; anything else (a transport error, a timeout, a
  cancelled context, a 5xx, a panic) **could not be told**: nothing is deleted, the name is never cleared (a delete's 404 does not prove a
  late create cannot land), and the key stays resumable; the next holder asks the backend by name;
- **no session recorded in the row**: the session this agent's own workload identity opened for the trigger's task (live or closed) is
  found by its task id and accounted for, so a session a person ended in the window before `Opened` is not followed by a fresh one. A session
  that could not be tied to the row is closed `unrecorded` and is replaced;
- a session this gateway no longer knows: `deduped`; none found: the trigger starts from the beginning (the same validity).

A **poison event** is one on which the code itself fails on every delivery (a panic). Only that counts; a "could not tell" (a backend,
the hold store, any dependency that did not answer) is an outage, never counted, never decided and never a reason to delete a run,
however long it lasts. The rule: each failed attempt is counted on the ledger row (`failures`, `first_failed_at`, `last_failed_at`, three
columns the Go gateway adds; they survive a restart), a failure more than an hour (`triggers.PoisonQuiet`) after the one before starts the
count again (a failure from hours ago is not part of it), and when 8 are counted (`PoisonAttempts`) with the first and the last at least 10
minutes apart (`PoisonAfter`) the trigger is decided. If its session's run is recorded launched, it is decided `launched` from the record
and the run is left to its session (never deleted because the event kept failing); otherwise the session's run, if any, is deleted and its
absence confirmed through the backend first (one that cannot be confirmed keeps the key undecided), and the trigger is decided
`launch-failed`. Either way rule `CT-POISON` is in the event history, with a log line and the metric `poisoned`, and the cursor moves on.
Until then the metric `stuck` (attempts of the failing trigger) and the cursor's lag (`cursor_time`) are exposed; alert when the cursor
lags more than 15 minutes, or `stuck` is above 3. The scheduler has no cursor to block and does not poison a slot.

The catch-up (`Resume`) moves the cursor only past events whose triggers were all decided; a catch-up that ends early (an error, the
context) reports `failed` and is run again from the saved cursor on the next stream, instead of being counted as done.

**How this table is made.** `TestEveryCrashWindowOfTheRealCodeKeepsTheTriggerOnceAndSafe` (gateway/internal/dispatch) drives the real
code (the bridge's takeover, `LaunchTriggered`, `launch`, the person controls, the sweep) over the real session store, with a fault
injector in place of the session database, the ledger and the run backend, and a run backend that keeps state (the runs that exist, every
create ever committed). A crash is the Nth durable call of the first process: it completes, and every later call of that process fails
without effect; fresh objects then take over. A clean run counts its calls, and each one is crashed at, for a plain launch, for a hold, an
end and a freeze placed before each call (and at the start of the takeover), and for each class of backend answer (timeout before the
commit, timeout after it, a create whose answer is lost and which lands later, a refusal) at each backend call, with the first takeover
also run against a backend that is down. The event arrives once by the stream and once by the catch-up (`Resume`, with the cursor). After
the takeover and after the deadline's sweep it asserts, against the backend's state: at most one run is ever created for the key; no
`launched` row without a run that was made (and a live session's run is live); no run is live under a decision other than `launched`; no run
is created after a hold, an end or a freeze, and none is live after a hold or an end that came before the decision, and at the moment a decision other than `launched` is written (the code's own claim: asked of the backend then); nothing is left live that
no session names; the cursor is never past an undecided trigger; every key ends decided after a clean takeover. A person's end or freeze is also made to land inside each save (after its record is written, while the save is still in progress), the core is made unreachable before each call, a delete that answers 200 and leaves the run is a fault class (only a GET says so), and poison and hold-store outages run as multi-delivery faults. The windows in which a run may be live although a hold or an end was placed are exactly three: a hold or an end that lands inside the create call itself (the check after the create undoes it before the decision), one that lands while the decision is being written or after it (the launch is past its last check; the sweep ends the run at its deadline), and a run whose create's answer was lost and which lands later (the name is kept, so the sweep deletes it).

The clean run's durable calls are the windows (the same list with the catch-up's cursor write after the decision):

| Window | Durable call it follows | The database and backend hold | Takeover outcome |
|---|---|---|---|
| 1 | the claim | the row `claimed`, no session | the session of the task is looked for; none, so the trigger runs from the start (`missed` when no longer valid): one run |
| 2 | the session is saved | a session of the task; the row `claimed` without it | found by its task id and recorded (`Opened`); launched: one run. A person's end or freeze here is read from the session: `refused`, no run |
| 3 | `Opened` | the row `claimed` with the session | launched (a hold stops it: `held`, session closed): one run |
| 4 | the run name is reserved | the session names a run; no `launched_at` | the backend is asked: absent, so created under the reserved name after the hold is read again; present, so it is the run; cannot tell, so resumable |
| 5 | the create (committed; the answer lost or not) | the run exists, no `launched_at` | a 409 or the backend's answer: the run is the session's own; the hold is read again after it and takes it away if one came (marker, close, delete, confirmed) |
| 6 | `launched_at` | the run exists and is recorded | decided `launched`; a hold placed since takes the run away first |
| 7 | the decision | the row decided | the replay is `deduped`; nothing opens (a hold, end or freeze now does not undo the launch; the sweep ends the run at its deadline) |
| 8 | the cursor (catch-up) | the cursor past a decided key | nothing to do |
| a | `run_removed` written (hold race, closed while made, record failed) | session live or closed, the run exists | closed, deleted, absence confirmed, then `held` / `refused` / `launch-failed`; a failed delete leaves the key resumable |
| b | a person's end, before or after any window above | closed `end` | the run, if there, is deleted and confirmed; `refused`/`CT-ENDED`; no create after it |
| c | the backend answers could-not-tell to a create | the name reserved; the run may exist or land later | nothing deleted, the name kept, the key resumable; resolved by the backend on the next takeover; a late landing run is ended by the sweep |
| d | the backend answers could-not-tell to a delete | `run_removed`, the run may exist | resumable until the delete is confirmed |
| e | the backend is down at the takeover | as at the crash | nothing is decided on a run that may exist; decided when the backend answers |

Other rows: `Decide` that cannot be written keeps the determined outcome in memory (bounded to 1000, the oldest evicted, dropped when the claim is
lost) and writes it as it was at the next claim; a ledger that cannot be read or written at the claim ends the stream and the cursor stays; a
hold that cannot be read before or after the run is retried (50 ms, 250 ms, 1 s) and then left undecided, never "no hold" and never
`launch-failed`; the holds copy is loaded at start, fails closed while it is not (or a write to the store errored), and a reload never overlaps
a hold write (one lock, whose waiters give up with their context, and each store call is bounded to 10 s); a trigger that panics is not
decided and the cursor does not move (it counts toward the poison bound above); an inbox request added before the call's session is saved
stays pending (counts toward the 5 a session may have) and the retry adds another; a human answer whose record is written before the process
dies is answered again and a second `human.answer` record is written (Python the same).

The ledger's `state` column is a closed set that Python's schema checks (`launched`, `deduped`, `braked`, `held`, `refused`, `launch-failed`,
`missed`), so no new value was added: a freeze or an end before the launch is recorded `refused` with the rule in the event history's outcome
(`CT-FROZEN`, `CT-ENDED`), a poison event `launch-failed` with `CT-POISON`, and a session whose launch is known to have happened is `launched`.
The read API and Tower read `state`, the session and the run, so nothing they know changed meaning.

The saves of one session are ordered (a record is built and written under one per-session lock), so a stale record can no longer overwrite a
later one (a person's end, written while an open was being saved); the harness found it.

The ledger change for the session needs no column: the row's existing `session` column is written while the row is still `claimed`, and Go's
takeover keeps it where it used to clear it. Python's claim clears `session` and `run` when it takes a `claimed` row over and never reads the
session of a claimed row, so Python is unchanged. A row Python wrote `claimed` has no session, and Go runs it from the start. A session row
carries three new keys in its JSON document, all Go-only and omitted when empty: `launched_at` (when its run was created), `close_reason`
(`control`, `by`, `at`) and `run_removed` (`reason`, `at`). Python reads a row by the keys it knows, so it ignores them and drops them at its
next save of that session (as with `delete_failure`).

**Rollback note.** After a roll back to the Python gateway and forward again to Go, the three Go-only facts (`launched_at`, `close_reason`,
`run_removed`) are gone from every session Python saved in between. Go then fails closed, with no relaunch and no double run: a session
read with no recorded close reason is `refused`/`CT-CLOSED`, so a deadline-close that was reopenable becomes a refused trigger, and a run
that was launched can be reported `refused` when its session is closed and its `launched_at` is gone (the run, if still live, is deleted by the
takeover like any run under a closed session). Before cutting back to Python an operator checks that no trigger row is `claimed` (the
ledger's `claimed` count is 0), that the event cursor has caught up, and that no `run_removed` is outstanding (no session whose run still
exists was marked removed): decided rows and their runs are unaffected, undecided ones are what the missing facts change.

A person's run (`RunAgent`): a crash after the core's open and before the session is saved leaves nothing (the core has the allow
record); after the save and before the launch, a live session with no run which the sweep closes at its deadline; a run that cannot be
launched is closed at once (Python leaves its session live). A freeze that crashes before its save leaves the session unfrozen and the
person freezes again; an End likewise (the sweep closes at the deadline in any case).

### What is deliberately not the same as Python (S3)

All of these leave the answer for ordinary inputs unchanged.

- **Authenticate first.** Python answers `404` for an unknown session or agent, and "not held" to a release, before it looks at the
  token or at who asks; an unauthenticated caller could learn which sessions exist and which agents are held. Go authenticates before
  anything, and tells a person who may not manage an agent nothing about it (a release is `CT-FORBIDDEN`, not `CT-NOHOLD`).
  An authenticated person still learns from `404` against `403` whether a session id exists (Python the same; the ids are random and
  the person is on the allow-list).
- **A delegate naming `user:`** (no name) is refused (400); Python goes on to ask whether a person with no name may manage the agent,
  which an admin glob such as `user:*` answers yes to. `hours` as a string of non-ASCII digits is refused; Python's `int()` reads it.
- **Freeze does not wait for a call in flight** on the session; the check that the session is live and not yet frozen and the trip are one
  step under the session's lock, so two freezes give one freeze and one `CT-TRIPPED`. Two Ends give one End and one `CT-CLOSED`, and one
  record. Two answers to one request give one answer, one record and `HR-ANSWERED`.
- **The holds are also kept in memory** (loaded at the first use, the store stays the source of truth at start): a hold or a release writes the store
  first and then, under the gate, the copy, one at a time. The gate is never held across a database call, so a stuck database stalls the person
  who is holding, never the opens and launches behind a pending hold. The `/v1` routes authenticate the caller once and hand the principal to the
  operation.
- **A hold is not delayed by a slow core, and it covers the launch as well as the open.** The hold gate is taken only to read the hold, and
  is never held across the core's decision, a save or a launch, so the emergency brake never waits behind them. A trigger's open (and a
  person's run) reads the hold before it asks the core and again, under the gate, right before it adopts the session: a hold saved
  meanwhile refuses the open (R024) and adopts nothing. A trigger's launch reads the hold before it starts and again after the run was
  made: a session opened before a hold, and launched after it, does not run (the session is closed and the trigger recorded `held`); a
  run that the hold overtook while it was being made is deleted again at once. So after the hold is acknowledged no session is adopted,
  and a run that began before it is at most briefly alive, never kept. Python gets this from its one lock. An expired hold is dropped by the
  sweep, not by the read that finds it.
- **A frozen session starts no run**: `Launch` of a tripped session closes it and refuses (R004). This applies to a person's `run_agent` too.
  (Python launches a run for it that can only be refused.) A canary comparison of the two gateways sees a frozen-then-launched session close in
  Go and run in Python.
- **A trigger dedupes only onto a session it opened**: the task id is a hash anyone can compute, so the live session the core names must be
  this agent's, for this task, with no parent, and its principal must be the definition's own service account (Python records no marker on
  a triggered session; the principal is what marks one, since a person's session is `user:...`). Anything else is refused (`CORE-REFUSED`),
  nothing is launched, nothing is made.
- **Freeze and end answer one `404` ("no such session", no agent named) for a session that does not exist and one that is not the person's to
  manage**; Python answers 403 and names the agent. The route cannot be used to find which session ids exist or whose they are
  (`TestFreezeAndEndDoNotTellAnUnknownSessionFromAForeignOne`; the Python-equivalence test pins the difference).
- **The caller is checked before the body**: every `/v1` route verifies the bearer token before it reads or parses the body (a bad token is a
  401, never a 400 or a 413), and before an inbox answers "this deployment has no human inbox".
- **The inbox listing is filtered by the store**, on the owner and group fields Python writes, with the limit (5,000) per person.
- **The event history's retention key is clamped** to [now - retention, now + 5 minutes]; the stored event keeps the time it carried. A
  far-future `receivedAt` would otherwise never age out and, with the size cap, push real history out.
- **`RECONCILE_WINDOW_HOURS` is at most 696** (the ledger keeps its rows 720 hours; the window stays a day shorter, so a finished run whose
  row was pruned is never in the window and launched again). Python allows 744. A larger value stops the start.
- **The event bridge's URL is https** (`GLIDEPATH_API_URL`), unless `GLIDEPATH_API_ALLOW_HTTP=1` (Go only, default off, one warning at start
  naming the host) or the host is a loopback IP address (127.0.0.0/8, ::1; tests and local runs). No host name is special (not `localhost`,
  not `.local`). The client uses no proxy from the environment (Python's urllib does), so the gateway's token goes only to the host named in the
  URL (a redirect is never followed either): the token is in the `Authorization` and `X-Glidepath-Authorization` headers of requests to
  that host and no other (`TestTheBridgeNeverFollowsARedirect`). The saved cursor can be moved by the stream at most 5 minutes ahead of the
  gateway's clock (an id from further ahead is handled but does not move it): a source that sends ids up to 5 minutes in the future makes a
  resume start that far ahead, so events glidepath-api stamps inside that margin between the real time and the id's time are not replayed
  from the cursor (the ledger, not the cursor, is what keeps a trigger once, and the sweep recovers a missed `pipelinerun.finished`).
- **The repeatable writes are rate limited**: a person (or a delegate naming one) may make 30 holds and 30 runs a minute (`CT-RATE`, 429),
  checked after the person has been, so nobody's allowance is spent by a caller who was refused. Python has no limit.
- **Old human requests are pruned** (30 days after they expired; Python keeps them for ever), and the event history is also bounded by
  size (the newest 200,000 rows; Python bounds it by age alone).
- **A person's run that cannot be launched leaves no live session**; a trigger whose launch failed closes its session; and a candidate
  that was refused leaves nothing in the candidate table (Python keeps what it was asked to run until later runs age it out).
- **A candidate's runtime image** must end in `@sha256:` and exactly 64 lowercase hex digits (never all zeros), an empty
  `RuntimeImages` allow-list refuses every candidate (Python allows any registry), and a glob must match the whole image: the bare-prefix
  fallback Python adds is gone, so `ghcr.io/team` no longer admits `ghcr.io/team-evil/x` (`TestCandidateImageCheck`). `RUNTIME_IMAGES_EXTRA` fills
  the list.
- **`score` takes at most 50 sessions a case** (Python: only the body's 64 KiB).
- **The grants are checked** (see the trigger rule); Python adopts the core's.
- **The bridge** reconnects with a bounded, jittered backoff (Python: a fixed 5 s), has the limits above, does not move its cursor past an
  event whose ledger write failed, ignores an id the cursor must not follow, remembers the last 5,000 event ids as Python does, and keeps a
  brake per agent that follows a change of `maxPerHour` (Python keeps the first it saw). The topic matcher is a table, not Python's
  recursion, which is exponential in the number of `#` words and whose input is an event's routing key. An event whose id is not in the form
  ids have is dropped (Python accepts any string). A stream that ends in the middle of an event does not deliver it (as Python's parser).
- **The Preflight fingerprint** is Go's own digest of the parsed definition (Python hashes its dataclass); the two gateways keep separate
  ledgers, so nothing compares them.
- **The summary's overflow** drops the largest value first (Python: the last inserted); the bound is the same.
- **A run's identity needs its pod** (the pod-binding rule, below), which Python does not check.

### What still refuses at the boundaries S3 leaves

- **The ledger change for the session**: no column was added. The row's existing `session` column is written while the row is still `claimed`
  (`Ledger.Opened`), and Go's claim takeover keeps it where it used to clear it. What Python does with it: Python's claim clears `session` and `run`
  when it takes a claimed row over and never reads the session of a `claimed` row, so Python is unchanged and will, if it ever shares the
  database with a Go-written claimed row, behave as it did (it does not see the session, so it can open another); and a row Python wrote
  `claimed` has no session, so Go opens as before (the live session of the task is still found by the core's dedupe). Both read the decided
  rows alike.
- **A candidate `document`** on `POST /v1/agents/{agent}/runs` answers `CT-NOTCARRIED` (501), after the person has been checked and before

### How each outbound URL is built

No argument an agent supplies chooses a scheme, host, port or the start of a path. Each URL is a configured base plus a fixed
path, or plus a path that has passed the rule below, and the finished URL of `app.api.get` is parsed again and refused unless
its scheme, host and base path are the configured ones.

| Backend | URL | What an agent's text can reach |
|---|---|---|
| `catalog.read` | `{BACKSTAGE_URL}/api/catalog/entities/by-query?` and a query string Python's order: `limit`, nine `fields`, then `filter` (a query containing `=`) or `fullTextFilterTerm` and three `fullTextFilterFields` | only the value of `filter` or `fullTextFilterTerm`, percent-escaped (`FuzzCatalogQuery`: whatever the text, the host and path are the base and the fixed path, and only the five parameters exist). At most 500 characters |
| `argo.app.get` | `https://kubernetes.default.svc/apis/argoproj.io/v1alpha1/namespaces/{ns}/applications[/{name}]` | the name, which must match the DNS pattern Python uses (lower case letters, digits, `.` and `-`, 1 to 253, starting and ending with a letter or digit) before any path exists; the namespaces are configuration, checked as DNS labels at start. A list adds `labelSelector`, `limit` and `continue`; the continue token is the API server's own and is escaped |
| `app.api.get` | the service's configured base (no trailing slash) + the path | the path: it starts with `/`, is at most 512 characters of `A-Za-z0-9._~!$&'()*+,;=:@%/-` and one optional `?query` of the same characters and `?`, has no `//`, no `%2e`, `%2f`, `%5c`, `%00`, `%25` in any case, no `%` that does not start two hex digits and no percent-encoded control character, and passes the decoded-segment rule below, so it has no scheme, host, userinfo, `#`, space, backslash or newline and cannot leave the base path. The service must be one of the configured names, matched exactly |

The decoded-segment rule for `app.api.get` (it decides on what a server will read, not on how the path is written, because a
server may decode before it strips path parameters or removes dot segments): the path before any `?` is split on `/`; each
segment is percent-decoded once; the decoded segment must hold only printable ASCII (0x20 to 0x7e) and none of `/`, `\`, `?`
or `#`; the part before its first `;` (a path parameter) must not be `.` or `..`. So `/..%3b/admin`, `/.%3b/` and `/a/..%3B/x`
are refused, as are overlong encodings (`%c0%ae`, `%c0%af`), invalid UTF-8 and every Unicode look-alike of a dot or a slash
(fullwidth U+FF0E and U+FF0F, U+2215, U+2044, U+2024, ...). Look-alike policy: refuse **every** non-ASCII byte in the decoded path
rather than keep a list that could miss one; an application's own API paths are ASCII (a path with an accented letter must be
written in the query, where only well-formed UTF-8 is required). The bytes sent are exactly the bytes validated.
The fuzz oracle does not use this rule: it decodes the accepted path once and twice, reads it with backslashes as slashes or not,
and strips parameters and removes RFC 3986 dot segments in several orders, and fails if any reading leaves the base path or the
host.

The Kubernetes reader allows one path shape, GET only: Applications of one namespace, listed or read by name, with the three
query parameters above. Python's reader also allows Airframe XR kinds and Rollouts (for `airframe.*`, S5c); Go's does not
yet. A path or query outside it is refused (`AF-K8S-PATH`) before a request exists.

### Credentials, redirects, sizes and time

- The Backstage token and the service-account token are read from their files on every call, stripped of white space, sent
  only to the configured host, and never logged, never in an error, a record or a result. An unreadable file is the error
  class Python's `open` raises (`FileNotFoundError`, `PermissionError`), with no path. `app.api.get` sends no credential and no
  cookie, only `Accept`.
- A redirect is never followed, by any of the three. Python follows one for `catalog.read` and `argo.app.get` (urllib's default
  opener) and sends the bearer token to the new host (shown: a 302 from the catalog host to another host receives the
  `Authorization` header). Go reads a 3xx as the answer: `catalog 302` (`ReadError`), `API server 302` (`AirframeError`), and
  for `app.api.get`, as in Python, `status: 302` as data. `TestARedirectIsNeverFollowedAndNoCredentialGoesToItsTarget` serves a
  second host and requires it saw nothing.
- The cluster API server is verified against the cluster CA file (`/var/run/secrets/kubernetes.io/serviceaccount/ca.crt`, re-read
  when it changes; TLS 1.2 or later; no skip of verification; a CA file with no certificate is an `SSLError`). Catalog and
  application API hosts use the system roots for https, and plain http only when the operator's URL says http: no host name is
  special.
- Each answer is read to a cap: 256 KiB for `app.api.get` (more is cut and reported `truncated`), 4 MiB for the catalog (Python:
  16 MiB), 16 MiB for the API server (as Python). More than the cap is an unparseable answer, class `JSONDecodeError`, as
  Python's truncated read is. JSON nested deeper than 256 levels is refused before it is decoded (an `app.api.get` body that
  deep is returned as text). Timeouts: 30 s for the catalog and the API server, 10 s for an application API (Python's), and every
  request also carries the call's own deadline.
- An upstream's body is never echoed beyond what Python echoes: a catalog 400's first 500 characters, an application API's
  body as data (it is the agent's own request), and nothing else. Any other status is `ReadError: catalog 502` and its kin.

### Artifacts: who can read and write what

An artifact belongs to a **task**, never to a session. The key is the session's task id and the name. A top-level session's task
id is the core's grant's; every child run, at any depth, has its parent's (`session.AdoptChild` refuses a grant that names
another task), so the whole run tree reads and overwrites the same artifacts, a sibling's included. A session of another task
(another person's, another agent's, a later run of the same agent) neither reads nor replaces them: it asks for a name under its
own task id, which is another row, and there is no list and no read by task id. A session with no task id has no artifacts (Python
would key them all on the empty string and share). This is Python's rule; `TestArtifactsAreKeptByTask` pins the parent, child,
grandchild, sibling, another person's, a later run's and a task whose id begins the same, and the dispatch test runs it through
`Gateway.Call`.

Limits, as in Python: a name is 1 to 100 of letters, digits, `.`, `_` and `-`; content is a string of at most 256 KiB (counted in
UTF-8 bytes); a task keeps at most 32 artifacts and 2 MiB; an artifact is gone 7 days after its last write; a put with an
existing name replaces it (and frees its bytes in the count). An artifact comes back as a string inside a tool result, never as
a document with a content type, so nothing sniffs it into something that runs. Concurrent puts for one task are serialized by a
lock on the task in the database, so two cannot both take the last place (`TestConcurrentArtifactPutsRespectTheQuotaInPostgres`).

Artifact storage is bounded per task (32 artifacts, 2 MiB, 7 days) but not globally, as in Python, so the table grows with the
number of tasks until their artifacts expire.

With `ARGO_ENABLED` on (the default) and no RBAC to read Applications, the gateway still starts and each `argo.app.get` call is
refused cleanly (`AF-K8S-403`, one outcome); nothing is checked at start.

### A spawn that lands while its parent is being closed (S2 code, looked at in S3)

`CloseTouched` snapshots a session's children, closes them, then closes the parent. `AdoptChild` refuses a parent that is closed, but the
parent is closed last, so a spawn landing between the snapshot and the close adopted a child under a parent that was still open and the
child was left live under a closed parent until its ttl: a real gap. The close now sets the parent closed, then reads the children again
(nothing can be added after that, `AdoptChild` refuses) and closes what was added in the window, returning those sessions to be saved
(`TestAChildAdoptedWhileTheParentIsBeingClosedIsClosedToo`, which stops the close between the snapshot and the close with a hook).

| `POST /repos/{owner}/{repo}/git/trees` | the files, on the base tree (plain blobs) |

There is no merge, review, approval, `PATCH`, `PUT` or `DELETE`, no branch protection, ruleset, workflow, label, comment or issue

branch, change protection, or write to an existing or default branch. The ref body is checked at the client: it must be
`refs/heads/` and a branch that passes the new-branch rule, with a commit id. A test asserts that no endpoint of the list contains a
merge, review, branch, protection or workflow path.

### Credentials

- The **glidepath-api token** and the **Kubernetes token** are the gateway's own projected service account tokens, re-read from
  their files on every call (`TestTokensAreReadOnEveryCallAndNeverEscape`) and sent only to the configured host. Nothing keeps one.
- The **GitHub App key** is not here and never was: Python does not hold it either. For each call the gateway asks Glidepath's
  broker for an installation token (`POST /agent-installation-token`, as its own identity with a projected token for the
  broker's audience, `AGENT_TOKEN_FILE`, re-read on every call). The broker checks that the repository is an onboarded app's own
  and down-scopes the token to that one repository (contents and pull requests write, never workflows); the gateway asks for one
  repository and no permission set of its own choosing, and Go is the same as Python here. The token is **minted per call**: it is a
  local variable of one call, used for that call's requests and dropped; never cached, logged, written to disk, put in an error,
  a record or a result.
- An upstream that echoes the credential it was given (an error message with the `Authorization` header in it) cannot put it back:
  every answer is read with the token taken out (`[redacted]`) before any text of it is used (Python repeats it).
- A redirect is never followed, by any of the four clients (`TestAWriteBackendsRedirectIsNeverFollowed...` serves a second host
  and requires it saw nothing); the `Authorization` header goes to the configured host only. The token is never in a URL.
- A token with a line break, one shorter than 12 characters, or an installation token with a character outside `A-Za-z0-9._~+/=-`, is
  refused rather than sent; `serve` does not start with a token file whose token is shorter than 12 characters. Redaction takes a token
  out of an answer whatever its length.
- `GLIDEPATH_API_URL`, `BROKER_URL` and the GitHub API URL must be `https` unless the deployment says otherwise:
  `GLIDEPATH_API_ALLOW_HTTP=1` and `BROKER_ALLOW_HTTP=1` (both Go only, off by default; the lab render turns them on) allow plain
  http, and `serve` then logs a warning. No host name is treated as special.

### When the answer is lost, or the process dies

There are three places a write can stop: before the remote system did it, after it did and before the gateway knew, and after the
gateway knew and before the outcome record is written. The core already holds the allow decision (written before the handler
runs); the outcome is the one record that follows.

| Write | Answer lost after the write (a timeout, a reset) | The process dies after the write, before the outcome is posted |
|---|---|---|
| `glidepath.run.rerun`, `promote`, `rollback` | the outcome reads `error:GlidepathError: glidepath-api unreachable: TimeoutError (the request was sent and no answer came: the write may have been made)` and the agent is told the same, plus that asking again with the same arguments is safe: the key is the session, the app and the run (or the promotion), so glidepath-api replays its first answer and starts one run (`TestARerunWhoseAnswerIsLost...`) | the decision has no outcome in the chain; the run exists; the agent's retry (or a replayed call) carries the same key and starts no second run |
| `glidepath.run.cancel` | the same text; cancelling twice is harmless | the same |
| `repo.pr.open`, `repo.pr.open_upper`, `glidepath.cicd.propose` | each POST that was sent and not answered is looked into once with a GET before anything is said: a lost ref answer is a branch that holds the commit this call made (the call goes on to the pull request); a lost pull request answer is found by its branch and returned. Only if the look also fails does the call say `GitHubError: ... (the request was sent and no answer came: the change may have been made)`, in the outcome and to the agent. A lost tree or commit answer leaves objects nothing points at, no branch and no pull request | a branch with no pull request (the PR step never ran), or a pull request the gateway never reported. A repeat of the same call is refused `GH-BRANCH-EXISTS` and opens nothing; **never a second pull request**. `EnsurePR` (what `airframe.apply` will use) resumes: it returns the pull request the branch has, or opens it once the branch's files are checked to be the ones asked for. The pull request then has no receipt (no `effect` on an outcome that was never posted), so the agent gates cannot vouch for it and a person looks at it: the same as Python |
| `argo.sync.lower` | `error:ArgoSyncError: API server unreachable (the request was sent and no answer came, so the sync may have been requested)`, and the agent is told to read `argo.app.get` before asking again. The patch carries the resourceVersion that was read and a marker with the session id; a second call that finds an operation in flight with its own session's marker answers `requested: true, replayed: true` (one sync, `TestASyncWhoseAnswerIsLost...`); another session meets `ARGO-BUSY` | the operation is in flight; a repeat is as in the left column |

A retry that comes after the first sync finished is a new sync: nothing can tell it from a deliberate second call. A call whose
time runs out after its write finished is reported as finished, not as a timeout (`dispatch.Gateway.KeepAnswer`, set by `serve`
to `backends.RemoteWrites`); Python's timeout never applies to a handler. Nothing is retried that writes: a write is sent once, and
only a read that is answered 429, 502, 503 or 504 (or a 403 that says it is a rate limit) is tried again, up to twice with a growing wait
that honours `Retry-After` and GitHub's `x-ratelimit-reset` and is never longer than 5 s or past the call's deadline.

### The receipt, and the replay's `effect.repo is owner/name`

The effect a write's outcome carries (`repo`, `paths`, `merge`, `needsPerson`, `pr`, `commit`, `branch`) is made by `dispatch.Effect`
from the call's arguments and its result, and the equivalence test holds it equal to Python's `_effect` for every case that returns. The
values are validated ones: a result's `repo` is the validated `owner/name`, its paths are normal paths, its branch passed the branch
rule, its commit is a hex id. The marks of the propose class are made here from glidepath-api's verdict and from nothing the agent
says.

The replay logs one `clearance core refused recordOutcome: HTTP 400: effect.repo is owner/name`. Its cause: the corpus has allowed
calls whose `repo` argument is not ASCII (`jfillman/ας`, `jfillman/İx`; the core's glob allows them and Python's tests used a fake
git that accepted anything), the replay's stub handler reports success for any call, and `dispatch.effect` writes the **argument**
lowercased into the receipt, where the core requires `owner/name` of letters, digits, `.`, `_` and `-`. It is the stub, not the
gateway: with these handlers such a repository is refused (`GH-REPO`) before any request, so a success always carries a valid
repository. The line stays in the log because the corpus is not edited.

### Limits

Each backend has its own client, pool, timeout (30 s; the watch stream 120 s at most) and limit on requests in flight: glidepath-api
16 (8 for streams), GitHub's API 16, the broker 8, Kubernetes 8, so a slow backend holds its own share and no other
(`TestABackendThatIsSlowHoldsOnlyItsOwnShare...`). An answer is read to a cap while it is read: 8 MiB for a good one and 64 KiB for any
other (Python's), 256 KiB tail for logs and reports, a stream line 4 MiB and a stream 32 MiB. A request body is at most 300 KiB for
glidepath-api and 8 MiB of files for a pull request. A retry never repeats a write.

### Where definitions come from, in what order, and who can write them

1. **The bundled definitions**: the image's `agents/` directory (`AUTOPILOT_AGENTS_DIR`). They are the platform's own, reviewed with the image. A
   file that does not pass (the schema, a strict reading, a name that is not its file's) stops the start, as in Python. They come first in the set
   and can never be shadowed: a pin that names a bundled agent is rejected and listed, not loaded.
2. **Agent XRs** (`catalog.hangar.io/v1alpha1` `Agent`, Airframe's `xrds/agent.yaml`): an XR pins one commit of a definition file in an app's own
   repository (`spec.source.repo`, `path`, `commit`) and names the owning team (`spec.owner`). The loader lists the XRs, fetches each pinned file
   once per commit through the agents' GitHub App (`GitHub.ReadFile`: the per-call token from the broker, which allows an onboarded app's own repositories
   and nothing else), and decides each pin. An unreadable or invalid pin is a rejection with its reason; the rest load.
3. **The stored set** (`gateway_definitions`), loaded at start when the loader is on so a restart does not unload every pinned agent while
   the first poll is on its way. Each stored row goes back through the same decision a pin does (the schema, the strict reading, the pin rules and the
   policy below); a row that no longer passes is a rejection that says so, not a silent drop. With the loader off, stored rows are **not** loaded
   (nothing would keep them up to date); the log says how many there are.

**Who may write what the loader reads, and what the policy guarantees against them.** Python lists `catalog.hangar.io` Agent XRs in **every** namespace of the
cluster and trusts what it finds. The Go loader reads only the namespaces it is told to: `AGENT_XRS_NAMESPACES` (no default; the loader will not start without it),
one namespaced list each, so the access it needs is `get`/`list` on `agents.catalog.hangar.io` in those namespaces and nothing cluster-wide (at S7 the gateway's
ClusterRole becomes a Role in each listed namespace). An XR in any other namespace is never read, and an item that is not in the namespace that was listed is dropped
and logged. The setting refuses a wildcard, an upper-case or malformed name, more than 20 namespaces, and the namespaces an agent run or the platform controls
(`agent-*`, `autopilot-runs`, `kube-*`).

**The namespaces that are listed are app teams' own** (`app-<app>-cicd`, where the live pin `gate-reader` is): whoever can create an Agent XR there can write one, so
nothing the XR says is trusted. What the pin policy guarantees against an author in such a namespace, at load, on every reload and on stored rows:

- **Only its own app's repository is read.** The XR's repository must be `<owner>/<app>`, `<owner>/gitops-<app>` or `<owner>/gitops-infra-<app>` for the app the namespace
  names, with an owner in `GITHUB_OWNERS`; it is checked before any token is minted, so another app's repository (a `gitops-` repository included) is never fetched. A
  namespace that is not `app-<app>-cicd` is refused: there are no exempt "platform" namespaces (the platform's own agents are the bundled ones, which are not pins).
- **A published reason never quotes the file.** The reason a rejected pin is published with (to the core, the store and the read API) is a rule id and a place
  (`DF-SCHEMA profile/limits/ttlMinutes`, `DF-STRICT`, `DF-YAML at line 3`, `DF-POLICY profile/tools`, `DF-NAME`, `DF-OWNER`, `DF-IDENTITY`): never a value, a key or a name out of the
  file. The whole story is in the gateway's log (`agent pins: a pin was rejected`, with `detail`).
- **Nobody can take another team's agent away.** An agent name belongs to the namespace that holds it. A second namespace's XR of the same name is the one refused
  (`DF-NAME`); the holder keeps the name, also across a restart (the stored set is loaded before the first poll). Python rejects both, so anyone who could create an XR
  could remove an agent; a name two namespaces ask for at once, with no holder, still goes to neither. (A name that must start with the app was the alternative; the live
  pin `gate-reader` shows the platform does not name agents that way.)
- **One tenant cannot fill the budget.** At most 32 XRs per namespace (the first by name), a pin file of at most 24 KiB and a definition of at most 12 KiB, at most 32 entries in
  a list (tools, repository patterns, deny paths, ...) of at most 256 bytes each. The publish size is computed before the live set is changed; over the budget, the pins of the
  namespace that takes the most are dropped with `DF-BUDGET` (the others are untouched), so the gateway never runs a set the core was not given.

### A bad definition, and a failed reload

- **One bad pin does not take down the set and does not silently drop the others.** Each pin is decided on its own: the valid ones load, the bad ones are
  rejected with the reason (the team sees it in the read API and the core records it once as `definition.reject`), and the loaded and the rejected
  are published together in one request. A name two namespaces ask for at once, with no holder, is a rejection of both; a held name stays with its holder. A bundled definition that does not pass stops the start.
- **A reload that fails keeps the last good set and says so.** A list that fails (the API server, RBAC, a kind that is not served: a 404 is an error here,
  not an empty list), a list over 256 XRs, or every pin unreachable, applies nothing: the set the gateway runs and the set the core holds are unchanged,
  and the log says `keeping the current set` every poll (a warning, and an error from the third failure in a row), until it works. A pin whose file cannot be fetched for a reason that may pass
  (GitHub or the broker unreachable) is skipped: whatever was loaded for it stays. Only a reason that will not change (no such file at that commit, not YAML,
  the broker's refusal, the schema, the rules) rejects a pin.
- **An empty answer is not read as "no definitions" on one reading.** A successful list of zero XRs after a set that was not empty is applied only when the
  next poll says the same (a transient empty list must not unpin every agent for a minute, and the publish would tell the core so). The first poll, with nothing to
  lose, publishes at once.
- A publish that the core did not take (down, 5xx, a refusal) leaves the set applied in the gateway and **unpublished**; the next poll, changed or not, publishes
  the whole set again. A set that changed while a publish was in flight is published again, not marked as published. A set larger than the core takes (4 MiB) is
  not sent and says so.

### The publish contract

`PUT /v1/definitions` with `{provider, pins, rejected, bundled}`: every loaded pin as its source, owner and document; every rejection as its name, source and
reason; every bundled definition as its name, the gateway build (`AUTOPILOT_GATEWAY_VERSION`, as `bundled_version`) and its document. The request is built
from one snapshot of the bundled definitions, the pins and the rejections taken together under one lock, with the version of the set they belong to; one
publish runs at a time. It is **atomic from the gateway's side** (the core replaces the provider's whole set; the gateway never sends a part), **idempotent**
(the same set again changes and records nothing at the core, so the client retries it as it retries an evaluation) and never shrinks the set on a read error
(see above). It uses its own client with the 5 s attempt timeout and its own breaker, so a slow publish never counts against the decision path. A core that
predates the `bundled` field refuses the request as an unknown field: the set is sent again without it, and without it from then on. What was published is
logged as `definitions published` with the counts of pins, rejections and bundled definitions, the SHA-256 of the request's content, its size, and what the core
said it changed and now holds. (The trigger and expiry counters are not served until S6, and neither is a publish counter: the log line is the record.)

### What a pin may not have (Go only, each in the fixtures with a `why`)

A definition arrives through an app's repository, so a pin is held to more than the schema. These apply to pins (and to the stored rows), not to the bundled
definitions, which are the platform's own (`jfillman/*` is in a bundled definition and stays), and not to a candidate `document`, which is a pull request's
version of a live agent, possibly a bundled one, and is clamped before it runs:

- **The pin's commit** is a full commit id (40 or 64 lower-case hex digits). Python reads whatever `spec.source.commit` says as a git ref, so a branch or a tag
  is fetched once and then held, the version of whenever it was first seen; a pin has to be immutable for the review it stands for to mean anything.
- **Tools** are on a platform allowlist: `AGENT_XRS_TOOLS` when set, else the read tools (tier 0) and `repo.pr.open`, `glidepath.cicd.propose`, `human.request`, `artifact.put`.
  Not in a pin unless the platform lists them: `glidepath.promote`, `glidepath.rollback`, `argo.sync.lower`, `airframe.apply`, `run.spawn`, `run.close`, `xr.request`,
  `repo.pr.open_upper`, `glidepath.run.rerun`, `glidepath.run.cancel`. (Python takes any string.)
- **Tier ceiling**: at most `AGENT_XRS_MAX_TIER` (default `T2`, the schema's own highest; the schema has no `T3`).
- **`repos.allow`**: lower case, the owner in `GITHUB_OWNERS`, and each entry one of the app's own repositories written out (`<owner>/<app>`; `<owner>/gitops-<app>` only with the
  upper pull request tool in the pin's tools, which the default list does not have). No wildcards, so no pattern that reaches beyond the app by a case or a glob trick.
- **`profile.glidepath.apps` and `profile.airframe.apps`**: the app of the namespace, and nothing else.
- **`identity.serviceAccount`**: a workload pin's is `autopilot-runs/<name>` (Python's rule: the run identity namespace; a team cannot name another's); a delegated pin names none.
- **Event triggers**: a Glidepath event whose key starts `<app>.` (never `#`, `*.`, or another app's key); alert and RabbitMQ events have no reader and are refused.
- **Runtime image and sidecar images**: on the platform's list: the images the bundled definitions run and `RUNTIME_IMAGES_EXTRA` (whole-image globs); the digest is the schema's.
- The deny paths and fields only extend the baseline: a definition's `denyPaths` and `fieldDeny` are added to `BASELINE_DENY_PATHS` and `BASELINE_DENY_FIELDS`, never replace
  them (unchanged from Python, pinned by the bundled definitions' scopes).
- **A refusal that is about the repository's state, not the commit's** (the broker's "not an onboarded app's repository", no such file) is asked again after 5 minutes, so an
  app onboarded later or a file pushed later is read; one about the content stays for that commit, which cannot change.

**The live pin** `app-gate-api-cicd/gate-reader` (`jfillman/gate-api`, `agents/gate-reader.yaml` at `7f8d9657cb94...`, read from the repository and kept in
`testdata/gate-reader.yaml`) is **accepted** under this policy with the default tools, `GITHUB_OWNERS=jfillman` and the bundled runtime image (`TestTheLivePinGateReaderStillLoads`):
a T0 workload agent with three Glidepath read tools, `glidepath.apps: [gate-api]`, `autopilot-runs/gate-reader`, a manual trigger and the bundled runtime image. Nothing in its
repository has to change before the cutover.

### What is deliberately not the same as Python (S4)

Each is a case in `testdata/definitions.json` with `go` and `why`; the test fails on a `go` without a `why`. All leave the answer for an ordinary, well-written definition unchanged.

- **A pattern's `$` matches only at the end of the text.** Python's `re.search` lets `$` match before a final newline, so `description`, `owner`, a repository glob, an app glob,
  a runtime image and a trigger's key that end in a newline pass Python's schema. Here they do not: the text is what the reviewer saw.
- **An integer is a whole number written as one.** Python's `jsonschema` takes `20.0` as an integer, and `ttlMinutes: 20.0` then flows to the core and the manifests as a float.
  A fraction is refused by the schema as in Python (`1.5 is not of type 'integer'`); `20.0` is refused too. Integers above 2^53 are refused.
- **YAML is read strictly**, where Python's `safe_load` is lenient YAML 1.1: a repeated key is refused (Python keeps the last), an anchor, an alias, a merge key and an explicit tag are
  refused, a mapping key must be a string, `yes`/`no`/`on`/`off` unquoted, an integer in octal, hex, binary, with underscores or as `1:30`, an exponent, `.inf` and a date are refused
  (Python reads them as a boolean, an integer, an integer, an integer, a string or a float, a float, a date), a control character in a value is refused, a file over 64 KiB, 5,000 nodes or
  24 levels is refused. The reason reads `<file> is not acceptable: ...`. Python's own syntax-error text is libyaml's and Go's is another parser's: both read `is not valid YAML: ...`
  and differ after that.
- **A pin is bound to its app, redacted, and quota'd** (the guarantees above; Python reads any repository an onboarded app has, quotes the file in the reason, rejects both
  XRs of a name, and publishes whatever size the namespaces make). In the fixtures: every `policy` case (tools, delegated service account, another app's reads, repositories
  and event keys, images, list and size caps) and every corpus case that Python loads and the app-bound policy refuses (`acme/gate-*`, an app glob of `gate-*`, a trigger
  `bindingKey` of `a.b.c`, an `alert` or `rabbitmq` trigger, ...) carries `go` and `why`. The published-reason, holder, quota and budget rules are Go-only tests
  (`pin_policy_test.go`), because the Python loader has nothing to compare them with.
- **The loader reads named namespaces**, not the cluster (above), and **a 404 on the list is an error**, not an empty list.
- **An empty list is believed on the second reading**, not the first (above).
- **The stored rows are decided again** at start, and only when the loader is on.
- **A non-string `spec.source` field** of an XR (which the XRD's schema forbids) is treated as missing; Python would write its `str()`. Timestamps in `loaded_at` have whole seconds.
- **A deleted pin is removed even while another pin is unreachable.** When some pin's file cannot be read, Python re-adds every definition the poll did not
  see, so an Agent XR that was deleted keeps its agent for as long as any other pin is unreachable (a revoke delayed by an outage). Go re-adds only the pins that
  were skipped (PR Lens, #110).
- **A fetch error that is not the broker's rule skips the pin** this poll; Python skips it only for a GitHub error and aborts the whole poll (keeping the set) for anything else.
- **The unpublished flag is not set when the store write fails**: Python raises out of the poll before it. The live set is what runs; the store is for the restart, and the log says it could not be kept.
- **The gateway database holds two rejections of one name** as one row (the table's key is `(name, state)`); Python's insert of both fails on the key.

With the loader off the gateway publishes the bundled definitions at start and every 30 s until the core has taken them (Python's `DefinitionsPublisher`). `XR_REQUEST_ENABLED`

changes, and a redirect is never followed.

### Crash points of the loader

| Point | What survives | Result |
|---|---|---|
| after the set is replaced in memory, before the store write | the live set; the store holds the last one | a restart loads the last stored set and the first poll finds the difference |
| after the store write, before the publish | the live set and the store | the next poll publishes the whole set (`unpublished` is set before the publish and cleared only by a publish that the core took of the set as it still is) |
| mid-publish (request sent, answer lost) | the live set and the store; `unpublished` stays set | the next poll sends the same set again; the core records nothing for a set it already has |
| a poll that panics | the loop recovers and polls again | logged as `poll failed` |

## The drift guard

`gateway/PORTED.json` lists every Python file the Go gateway ports, the Go paths that carry it, what of it
the Go gateway carries, what is left in it for a later slice, and the SHA-256 the file had when the Go code was last
brought level with it. `tests/test_gateway_go.py` fails when a listed file's hash differs. A hash cannot tell whether a
change matters to the port, so the failure asks the author to read it and do one of two things: port the change to Go in
the same pull request (with a test that holds the Go result equal to the Python one), or confirm it does not touch what the
Go gateway carries. Either way the next step is `python tools/gen_gateway_ported.py`, which shows what changed since the
manifest and records the new hashes. The manifest is not edited by hand; its tables live in the tool.

The guard is checked for being empty: the manifest must list a fixed set of core files (removing one to silence a change
fails), every listed file and Go path must exist, and a changed hash is shown to be reported. Every Python file under
`src/autopilot` is also classified, as ported, as belonging to a later slice (`not_ported`, with the slice) or as out of
scope (with the reason), so a new Python module fails the test until someone decides which. The three Clearance pins
(CI, `pyproject.toml`, `go.mod`) are checked to be one release.

Limits: it notices a change to a file, not to a behaviour that lives somewhere it does not list, and it cannot say that a
port is right (the equivalence tests do). Its use is that nobody changes a ported file without having looked at the Go side.

## Timeouts, pools and what never blocks

- Every tool call runs under a context deadline (`GATEWAY_CALL_TIMEOUT_SECONDS`, default 60). The backend sees it and
  returns when it ends; the outcome is still reported, under a fresh bounded context (`error:Timeout`).
- Every backend has its own HTTP client: its own timeout and its own connection pool (`backends/`), so a slow Loki
  cannot starve Prometheus. The Clearance client has its own pool and the outage policy's 250 ms per attempt, one retry
  and a breaker (the client's, unchanged); the model proxy has an upstream pool of its own.
- No process-wide lock. One session's operations are serialized (so a session cannot overspend by racing itself); other
  sessions run in parallel. The model proxy holds a session only for the decision and for the final charge, never while
  a response streams.
- A panic in a backend is an `error:Panic` outcome, not a crash. A failed save of sessions exits the process (crash-only,
  as the Python gateway does); the restart reloads them.

## Authentication

The Go gateway verifies the same three kinds of caller as the Python one (`src/autopilot/engine/auth.py`), chosen by
the token's issuer, behind the same one-minute cache:

| Caller | Verifier | Principal | Set by |
|---|---|---|---|
| a service account of this cluster | the API server's TokenReview | `<namespace>/<name>`, kind `workload` | `AUTOPILOT_RUN_AUDIENCES` (default `autopilot`) |
| a person (Dex in the lab) | the issuer's JWKS: signature, issuer, audience, expiry | `user:<claim>`, kind `user` | `AUTOPILOT_OIDC_ISSUER`, `AUTOPILOT_OIDC_AUDIENCE`, `AUTOPILOT_OIDC_ALLOWED_USERS`, `AUTOPILOT_OIDC_JWKS_URL` (default `<issuer>/keys`), `AUTOPILOT_OIDC_USER_CLAIM` (default `email`) |
| another cluster's service account (Tower's backend) | that cluster's public issuer's JWKS | `<TOWER_CLUSTER>/<namespace>/<name>`, kind `workload` | `TOWER_ISSUER`, `TOWER_CLUSTER`, `TOWER_SERVICE_ACCOUNTS`, `TOWER_JWKS_URL` (default `<issuer>/jwks.json`); the audience is `AUTOPILOT_AUDIENCE` (default `clearance`) |

List only run audiences in `AUTOPILOT_RUN_AUDIENCES`: naming another service's audience there makes that service's local
service-account tokens acceptable as workloads.

The variables, their defaults and their start-up checks are the Python gateway's (an issuer needs its audience and an
allow-list, `TOWER_ISSUER` needs a cluster name and service-account globs, trailing slashes on issuers are removed).
The allow-lists use Python's `fnmatch` rules (`*` matches `/`), reproduced in Go, not `path.Match`. The metadata's
authorization server is the OIDC issuer, else this server. The GitHub Actions verifier of `engine/auth.py` is ported
(`auth.GitHubActions`, with the `repository` attribute and the immutable-id `sub` form) and tested, but `serve` does not
wire it: the Python gateway does not either (since R-3b the core takes GitHub Actions callers, and `CLEARANCE_GITHUB_OIDC_*`
fail its start).

What the verifier accepts, and refuses without saying why (every refusal is the same `token rejected`, nothing from the
token is logged):

- Only `RS256` and `ES256` (the GitHub verifier only `RS256`), each tied to the key's type; never `none`, never HMAC, never
  another algorithm; a token with a `crit` header is refused. The key is picked by `kid`.
- `exp`, `iat`, `iss`, `aud` and `sub` must be present; `exp`, `nbf` and `iat` are checked with 30 seconds of leeway;
  `iss` and `aud` are compared exactly (an `aud` list must hold the audience).
- The routing step reads `iss` without trusting it, only to choose the verifier; a token for an issuer that is not
  configured goes to TokenReview, which refuses it, and a token that is not a JWT is refused.
- A cached success never outlives the token's `exp`; a failure is never cached.
- The JWKS is fetched over https, within 10 seconds, at most 1 MiB, following redirects only on the same host. Plain http
  is allowed for loopback hosts (local runs) and, for any other host, only with `AUTOPILOT_JWKS_ALLOW_HTTP=1` (a Go-only
  setting, off by default): the lab that serves Dex over http turns it on in its render, and `serve` logs a warning naming
  the host at start. Nothing in the code treats a host name such as `.local` as special.
- An unknown `kid` refetches the key set at most once a minute after a successful fetch, however many requests ask, and at
  most once every 5 seconds after a failed one, so a blip at the issuer does not lock sign-in out for a minute. The fetch
  runs detached from the request that triggered it (a caller that names an unknown `kid` and hangs up cannot cancel it);
  callers share it and leave when their own context ends. `serve` fetches each key set once in the background at start;
  a failed first fetch is a warning, not fatal.
- The key set is refetched every 10 minutes whether or not a token asks. A key the issuer removed stays trusted until
  the next refetch (the request that notices the age still uses the old keys), and for as long as the issuer cannot be
  reached: the same as Python, which refetches only for an unknown `kid`.
- Only a token whose signature has verified can start the 10-minute refetch, so an unauthenticated caller cannot drive it. An
  answer with no usable key counts as a failed fetch (the keys held are kept), and after a failure the retry waits 5 s,
  then 10, 20, 40 and at most 60 s, until a fetch succeeds.
- A token may hold only base64url characters and its two dots (anything else, a newline included, is refused before decoding).

Where it differs from Python on purpose (all stricter, or an error handled where Python's escapes):

| Go | Python |
|---|---|
| a token over 16 KiB is refused before parsing | no limit |
| a JWKS URL over plain http is refused at start unless the host is loopback or `AUTOPILOT_JWKS_ALLOW_HTTP=1` | any http(s) URL, any redirect, any size |
| a JWKS key that is not RSA (at least 2048 bits) or P-256 is skipped | one unreadable key makes the whole refresh fail |
| `exp`, `iat`, `nbf` must be JSON numbers | `int()` also accepts a numeric string |
| a failed JWKS fetch, or an `alg` that does not fit the key, is a refusal | raises an error that is not `AuthError` (the server answers 500, not 401) |
| refusals are all one message | the message names the reason (it is not sent to the caller) |

`tests/test_gateway_go_auth.py` feeds the same tokens to both and compares the answer (accepted or refused, principal,
kind, tier ceiling, attributes), and the allow-list globs and the `sub` canonicalisation too; the Go table tests
(`gateway/internal/auth`) cover every refusal above, and a fuzz target (`FuzzTokenParsingAndRouting`) holds that no input
is accepted and none panics.

## How it is proven equal to the Python gateway

1. **The R-3 replay corpus** (Clearance's golden corpus, `testdata/golden/corpus.jsonl`, recorded from the Python
   engine over its whole test suite). `gateway/internal/replay` replays it through the Go gateway's own code against a
   real, unmodified core (with Hangar's bundle, or without it for the lines recorded without the Hangar pack): for every
   line it can take, the evaluation the Go gateway builds equals the Python one field for field, the decision (allow,
   rule, name, message, hint, tier, problems) is identical, the spend leaves the session as the Python one did, the
   grant a `session.open` makes is identical, and the decision record the core writes has the corpus line's fields.
   Against clearance v0.44.0 (the CI pin): 342 tool calls, 292 session opens (261 a person's or a client's, 31 triggered), 35
   session spawns, 49 model calls; 372 spends, 679 records and 290 grants compared; zero differences. (Before S3: 261 opens,

   decision, the session the grant makes or the live one a dedupe names, and the record), so the gateway's check of a triggered
   grant (`checkOpenGrant`) is shown to accept everything the core makes too. Five tool calls are listed as decided differently on purpose since the corpus was recorded: Glidepath's
   contract v2 `propose` class changed the text of the Flight-environment refusals (`decidedDifferentlySince` in

2. **The conformance harness** that ships in the Clearance release (`clearance conformance --role runtime`) drives the Go

`XR_REQUEST_ENABLED=0`, because Python turns it on with it. S3 removed `EVENTS_ENABLED`: the event bridge
reads glidepath-api with the S5b settings, `GLIDEPATH_API_URL` (https unless `GLIDEPATH_API_ALLOW_HTTP=1`) and `GLIDEPATH_TOKEN_FILE`;
`SCHEDULES_ENABLED`, `RECONCILE_SECONDS`, `RECONCILE_WINDOW_HOURS`, `AUTOPILOT_DELEGATES`, `AUTOPILOT_ADMINS`, `RUNTIME_IMAGES_EXTRA` and
`PREFLIGHT_CASES_DIR` are read, with Python's checks. S4 removed `AGENT_XRS_ENABLED` and brought `AGENT_XRS_INTERVAL`; with the loader on, the Go-only
`AGENT_XRS_NAMESPACES` is required.)

Not ported, and still the Python gateway's:

- **The Backstage directory** (`BackstageDirectory`, `reads.py`; S5a classified it S6): the catalog client exists (S5a) but no group lookup is wired, so an agent's owner group resolves to nobody and only a session's person and the admins act until it is.
- **The runtime catalog** (`runtime/catalog.yaml`, `GET /v1/runtimes`, `runtimes.py`, S6): a candidate's image globs are
  `Gateway.RuntimeImages`, filled from `RUNTIME_IMAGES_EXTRA` alone.
- **Backends**: `metrics.query`, `logs.query`, `catalog.read`, `argo.app.get`, `app.api.get`, `artifact.put` and `artifact.get`
  are ported with per-backend timeouts and pools; S5b adds every `glidepath.*` tool, `repo.file.get`, `repo.pr.open`,
  `repo.pr.open_upper` and `argo.sync.lower`. The rest have no handler, so a call to them is refused as having no backend,
  as in a Python gateway that does not configure them: `xr.request` and `airframe.*` (S5c); `chat.*` (Python has none either).
  Python's read API also uses `BackstageDirectory` and `BackstageOwnership` (S6). Also left for S5c in `github_pr.py`:
  `commit_xr`, `pr_paths`, `repo_ready` and `onboarding_prs`; `ensure_pr` and `find_pr` are built here but no tool calls them yet.
- **The field scope of a file's YAML** (`repos.fieldDeny`, `fieldAllow`, AF-9a) is the core's: it needs the file as it was before.
  The gateway decides the repository and the path again, not the fields.
- **`api`** (clearance-api's runtime reads, `api_serve.py`, `read_api.py`, `reads`), the Prometheus endpoint on `METRICS_PORT` (the
  trigger counters are counted behind `triggers.Metrics` and not served),
  OTLP logs, and a `held` outbox reason (since clearance v0.28.0 the core takes every kind the gateway writes).
- **Release plumbing**: no `gateway-go-v*` tag, image workflow or Apron change. The Python image stays what
  `gateway-image.yaml` builds.

The 7-day canary, moving every definition to it, and removing the Python gateway are the managing agent's later steps,
after the remainder above is ported.

## Running it (locally)

```shell
cd gateway && go build -o autopilot-gateway ./cmd/autopilot-gateway
GATEWAY_DSN=postgresql://... CLEARANCE_CORE_URL=http://clearance-core:8080 \
  CLEARANCE_CORE_TOKEN_FILE=/var/run/secrets/tokens/clearance AUTOPILOT_AGENTS_DIR=../agents ./autopilot-gateway serve
```

It reads the variables the Python gateway reads, for the part it carries: `PORT`, `MODEL_PORT`, `GATEWAY_DSN`,
`CLEARANCE_CORE_URL`, `CLEARANCE_CORE_TOKEN_FILE`, `AUTOPILOT_AGENTS_DIR`, `AUTOPILOT_AUDIENCE`, `MODEL_TOKEN_AUDIENCE`,
`AUTOPILOT_OIDC_ISSUER`, `AUTOPILOT_OIDC_AUDIENCE`, `AUTOPILOT_OIDC_ALLOWED_USERS`, `AUTOPILOT_OIDC_JWKS_URL`, `AUTOPILOT_OIDC_USER_CLAIM`, `TOWER_ISSUER`, `TOWER_CLUSTER`, `TOWER_SERVICE_ACCOUNTS`, `TOWER_JWKS_URL`, `AUTOPILOT_JWKS_ALLOW_HTTP` (Go only),
`AUTOPILOT_RESOURCE_URL`, `AUTOPILOT_EXPIRE_SECONDS`, `GATEWAY_OUTAGE_ALLOW_READS`, `MODEL_ROUTES`, `MODEL_KEY_FILE`,
`AUTOPILOT_RUN_AUDIENCES`, `CLEARANCE_CORE_TIMEOUT`, `PROMETHEUS_URL`, `LOKI_URL`, `BACKSTAGE_URL`, `BACKSTAGE_TOKEN_FILE`,
`APP_API_SERVICES`, `ARGO_ENABLED`, `ARGO_APP_NAMESPACES`, `GLIDEPATH_API_URL`, `GLIDEPATH_TOKEN_FILE`, `GLIDEPATH_ON_BEHALF_OF`,
`GITHUB_PR_ENABLED`, `AGENT_TOKEN_FILE`, `BROKER_URL`, `ARGO_SYNC_ENABLED`, `LOG_LEVEL`, (S4) `AGENT_XRS_ENABLED`, `AGENT_XRS_INTERVAL`, `AGENT_XRS_NAMESPACES` (Go only) and `AGENT_XRS_MAX_TIER` (Go only), and (S3) `AUTOPILOT_DELEGATES`, `AUTOPILOT_ADMINS`, `EVENTS_ENABLED`, `GLIDEPATH_API_ALLOW_HTTP` (Go only), `SCHEDULES_ENABLED`, `RECONCILE_SECONDS`, `RECONCILE_WINDOW_HOURS`, `RUNTIME_IMAGES_EXTRA`, `PREFLIGHT_CASES_DIR`; `GITHUB_OWNERS` is Go's own too (it is required with
`GITHUB_PR_ENABLED`, and `XR_REQUEST_ENABLED=0` must be said); and three of its own: `GATEWAY_CALL_TIMEOUT_SECONDS` (60),
`MODEL_TIMEOUT_SECONDS` (300), `GATEWAY_PG_CONNS` (16). It takes the gateway database's writer lock, so it cannot run
beside the Python gateway on the same database.

`serve` reads the S5a variables as Python does (`BACKSTAGE_URL` and `APP_API_SERVICES` switch their tool on; `argo.app.get` is on by
default, in `argocd`, and needs the Role on Applications the Python gateway has; `ARGO_ENABLED=0` switches it off); the
catalog's token is the projected service-account token for the `backstage` audience, as before.

`serve` reads the S5b variables as Python does, except the three Go differences in the table above (`BROKER_URL` has no default,
`GITHUB_OWNERS`, the two flags that must be 0). The scope of every write is decided from the agent's definition (`Gateway.Def`),
looked up per call.

`serve` needs no new variable for runs: the run backend is the in-cluster Kubernetes API (as the Python gateway always uses it),
so the gateway's identity needs the Role on AgentRuns in `autopilot-runs` it already has.

Tests: `cd gateway && go vet ./... && go test -race ./...`. The replay needs a clearance checkout (`CLEARANCE_SRC`) and the
core binary (`CLEARANCE_CORE_BIN`); the database tests need a scratch Postgres (`AUTOPILOT_TEST_PG`); without them those
tests skip. `pytest tests/test_gateway_go.py` runs all of it with the suite's core, and the drift guard.
