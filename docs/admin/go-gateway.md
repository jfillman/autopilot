# The Go AI gateway (A-9)

**Status: people and Tower sign-in (A-9 S1) and runs and the run tree (A-9 S2, 2026-11-14) are in, on top of the first slice and
the catch-up (S0); built and tested, off by default, not deployed.** The Python gateway (`src/autopilot/serve.py`, the repo's `Dockerfile`, `gateway-image.yaml`) is
still the gateway on every cluster and is still the reference: it is **not removed**. Nothing selects the Go image until
the managing cutover does. This page says what the Go gateway (`gateway/`) already does, how it is proven equal to the
Python one, how it is kept equal ([the drift guard](#the-drift-guard)), and exactly what is left.

## What it is

One static binary, `autopilot-gateway`, on distroless static (nonroot, uid 65532, no shell: the same bases as
Clearance's image, `gateway/Dockerfile`):

| Subcommand | Does |
|---|---|
| `serve` | the MCP server (`PORT`, default 8080), the model proxy (`MODEL_PORT`, default 8081, only with `MODEL_KEY_FILE`), the expiry sweep (close, delete runs, backstop outcomes) and the outbox drain |
| `conformance-control` | the test-only conformance control interface; off unless `GATEWAY_CONFORMANCE_CONTROL=1`, loopback only |
| `api` | **not ported**: exits 2 and says so. The read API is still the Python `autopilot-gateway api` |
| `version` | the image's version (`AUTOPILOT_GATEWAY_VERSION`, else the build's) |

It is built on:

- **MCP**: the official Go SDK (`github.com/modelcontextprotocol/go-sdk` v1.8.0): streamable HTTP, stateless, JSON
  responses, a bearer token verified before any tool runs (401 otherwise), protected-resource metadata, `GET /healthz`.
  The tools it carries keep their Python names and result shapes: `tools_list`, `agents_list`, `session_open`, `call`, and
  (S2) `run_finish` and `session_close`; `run.spawn` and `run.close` are tools inside a session (`call`).
- **Clearance**: the Go client Clearance ships (`github.com/jfillman/clearance/client`, R-1e), pinned to the same
  release as the Python client and the test core (`CLEARANCE_REF` in `.github/workflows/test.yaml`, `pyproject.toml`,
  `gateway/go.mod`; bump the three together: `tests/test_gateway_go.py` fails when they differ). Autopilot's code reaches
  Clearance only through this API. The decision path asks for an answer within 1 s per attempt (`CLEARANCE_CORE_TIMEOUT`,
  0.05 to 30; the Clearance client's own default of 250 ms was shorter than a ledger append that took 306 ms live),
  retries a timeout, a connection failure or a 503 once, and opens its breaker after 5 consecutive failures.
- **The model proxy**: a streaming reverse proxy. A response body is relayed chunk by chunk with a flush and is never
  held: the first server-sent event reaches the run while the provider is still producing the rest. Usage is metered
  from the events as they pass (or from a bounded copy of a plain answer) and charged when the call ends, however it
  ends; every allowed call gets exactly one outcome (`ok`, `error:Upstream<status>`, `error:StreamInterrupted`, ...).
- **The gateway database**: the same tables, columns and writer lock as the Python gateway
  ([gateway-database.md](gateway-database.md)). `gateway/internal/pgstate/schema.sql` is generated from the Python
  `SCHEMA`; a session row either implementation wrote loads in the other. Sessions are saved durably after every
  operation, with concurrent saves grouped into one transaction.

Tool names, tiers, arguments, costs and the baseline deny lists are the Python registry's
(`gateway/internal/tools/registry.json`, generated by `tools/gen_gateway_registry.py`; `tests/test_gateway_go.py` fails
when it is stale). The bundled agent definitions parse to the same scope and agent the Python parser sends the core.
The same generator writes three more fixtures from the Python code, so a Go test can hold the Go result equal to the
Python one: session rows as `Session.to_record` writes them (`session/testdata/rows.json`, read and written back whole),
what the agent is told and the outcome records for each kind of backend failure (`dispatch/testdata/backend_errors.json`)
and the effect a write's outcome carries (`dispatch/testdata/effects.json`).

### The run's identity, in plain words

A caller acts as a session only when it IS that session's run. The gateway decides that from three things, all of which it
holds itself: the session has a run (a name the gateway wrote when it created the run, never taken from a caller), the caller
is a workload token that the Kubernetes token review verified, and the caller's verified identity (`namespace/serviceaccount`)
is exactly `agent-<run>/run` for that run, a name of `r-` and 6 to 32 hex digits. Then the gateway tells the core "this caller
acts as the session's principal", and the core decides as it would for the person. Nothing the caller sends is read: not an
argument, a header, a label or a name.

So these all act as themselves and are refused by the core as another principal's session (R001): a sibling run, a child
acting as its parent, a parent acting as its child, a run in another namespace with the same service account name, the run's
own namespace with another service account, a person whose id looks like a run's, a run of a session with no run (finished or
deleted), and a replayed token after `run.close`. Each is a test (`TestARunActsOnlyAsItsOwnSession`,
`TestAReplayedRunTokenActsAsNothingAfterItsRunIsGone`, `TestAClosedSessionWhoseRunWasNotDeletedStillAllowsNothing`).

Stricter than Python, deliberately: the caller must be a `workload` (Python only compares ids), and the run's name must be a
real run name. `acting.json` records Python's answer and Go's for each case; the two differ only for a user whose id is a run's
and for a run name no run has.

### What is deliberately not the same as Python

All of these leave the answer for ordinary inputs unchanged.

- **The gateway checks the core's spawn grant.** The core cuts a child's limits; Python adopts the grant as it is. Go also
  refuses it (R007, nothing created, one refused outcome) when it is wider than the definition's limits cut to what the parent
  has left, names another principal, task or agent than the parent's, reuses a session id, goes deeper than 3, outlives the
  parent, or reserves other than the child's limits. Budget, depth, fan-out, tools, models, tier, network and compute can only
  narrow from parent to child even if the core would allow more. Every grant the real core made in the replay corpus passes.
- **A spawn's check and reservation are one step under the parent's lock** (`Store.AdoptChild`), and one session's calls are
  serialized, so concurrent spawns cannot overspend a parent, even while the model proxy charges it. The storm tests run with
  `-race`.
- **Write-ahead of the run's name.** A run's name is saved with its session (and a spawn's reservation with the parent) before
  the run is created; Python keeps everything in memory until the operation ends. See the crash points.
- **A run that fails to be created is deleted again**, best effort, because a timeout can come after the API server took it.
  Python leaves it to its own deadline. A spawn whose call ran out of time after the run was made is undone too.
- **A session launches once.** A second `launch` of a session with a run is refused (R001); Python tries to create it again
  and gets the API server's 409.
- **A spawn's `input`** must be an object that fits the AgentRun's 4 KiB, and every label value in the manifest must be a
  valid Kubernetes label value: refused (R008, or `RunRefused` before any request) rather than left to the API server.
- **`run.close` with a `run_id` that is not a string** is refused R001; Python raises a TypeError.
- **A grant's parent must be the session that asked.** The check that the grant's parent is the calling session is Go's only;
  Python looks the parent up by the grant.
- **The sweep is bounded, which Python's is not.** Python retries a run whose delete keeps failing on every sweep, forever, and
  writes a `run.delete error:` record each time, and a run named by an ancestor and by its own entry is attempted again in the
  same sweep. Go retries on a backoff (1, 2, 4 ... capped at 30 minutes), records a failure when it starts and then at most
  once an hour while it keeps failing, records the success once, and handles each run at most once per sweep. A close by a
  person or a run always tries at once.
- **The failure state of a delete that keeps failing is saved with the session** (a `delete_failure` key inside the session's
  JSON document: attempts, first failure, last record, next try), so a restart continues the backoff and the hourly record
  limit instead of retrying everything at once. No schema change. The Python gateway reads a row by the keys it knows, so it
  ignores the key; its next save of that session writes the row without it and the backoff starts again. The first failure and
  each hourly record are also logged at error level, naming the run, the session, the error kind and the attempts. A person's
  or a run's own close always records its own result. The sweep's log line counts the sessions it actually tried, not those
  waiting out a backoff.
- **A session closed while its run is being created** (a person's End, the parent's close, the sweep) has the run deleted
  afterwards and the agent told, with the refund made once by the close; Python would leave a live run. A launch whose
  `run.launch` record cannot be written, and whose delete fails too, keeps the run's name so the sweep retries the delete.
- **`run_finish` checks again, under the session's lock, just before it sets the outcome**: a finish that lost to the deadline
  or the sweep's `expired` takes back the answer it stored and is refused R004.
- **The sweep's reads rotate** (each sweep starts after the last session the previous one reached) and its wait for them has a
  deadline of its own, so a mostly hung API server starves no session and a backend that ignores its context cannot hang it.
- **The sweep has one deadline and holds no session lock across the API server.** Closing the sessions past their deadline
  comes first and needs no API server; the reads of how runs ended run a few at a time (8) within the sweep's deadline, with
  no session lock held, and are applied only to a session that is idle (an operation in flight is looked at on the next sweep)
  and unchanged since the read. A child whose run is being made holds its operation lock until the run exists (parent first,
  then child, the only order), and its run epoch changes when the run is made, so the sweep cannot mistake the API server's
  404 for a run that does not exist yet for a run that is gone. Python reads each run in turn under the session lock.
- **`run_finish` for a session that is not the caller's run is always R001**, unknown, closed or another's alike, so the answer
  does not say whether a session id exists (Python answers an unknown or closed one R004 first). Its own run, after the session
  ended, is still told R004. A finish at or after the session's deadline, or after the sweep wrote `expired`, is refused R004
  and cannot overwrite that outcome; Python accepts it.
- **A spawn whose time ran out while its child was being saved** is undone or succeeds, never both: the answer is not turned
  into a timeout after the child's fate is decided.
- **A run's answer is saved before its session closes**, in two transactions (Python: one). A crash between leaves the session
  open and the run finishes again; the first answer is the one kept.

### Crash points

What the database holds if the process dies at each point, and what the next gateway does. The sessions are saved at each
step marked (save).

| Dies | Database holds | Next gateway |
|---|---|---|
| in a spawn, after the core's decision, before the child exists | nothing new (the core has the allow record) | nothing: an unused session id, no run, no reservation. Python the same |
| after the child exists in memory, before its save | nothing new | the same |
| after the write-ahead save, before the run is created (save) | the child, live, naming its run; the parent's reservation and the call's charge | the run does not exist, so no pod holds the child's identity. The sweep closes the child at its deadline, deletes the run it names (a 404 is success, recorded `deleted`), and the reservation comes back. Python: the state is lost whole, nothing to clean |
| after the run is created, before the call ends | the same row; the run exists | the child's pod can call (its session is known, so it is decided and recorded); the sweep deletes it at the deadline or when the session closes. Python: the pod's session is unknown to the restarted gateway, so every call is refused, and the AgentRun is left to its own deadline (the composition enforces it without the gateway) |
| a launch, after the write-ahead save, before or after the run exists (save) | the session naming its run | the same sweep |
| a launch's `run.launch` record cannot be written (core down) | the run was created; the record was required | the run is deleted again, the session names none (fail closed, as Python) |
| a finish, after the answer is kept, before the session closes | the answer; the session open | the run finishes again; the first answer stays |
| a close, after the session closes in memory, before its save | the session still live | the person or run closes it again; its budget was never returned in the saved rows |
| the run's delete fails | the session closed, still naming its run | every sweep retries and records each attempt (`error:KubeRunError`, then `deleted`) |

What a crash cannot undo: the evidence records the gateway wrote before it died (the core has them), and a run the API server
took after the gateway lost its connection to it.

### The namespace assumption behind run identity

The rule above rests on one fact outside the gateway: nobody but Crossplane (the AgentRun composition) can create a namespace
named `agent-r-<hex>` or a service account `run` in one. A principal with namespace-create, or with create on serviceaccounts and
tokens in such a namespace, could mint a token that passes the token review as a run and act as that run's session. So the
gateway's RBAC, the chart and the cluster's admission policy must keep namespace creation for `agent-*` names with the
composition's identity, and nobody else may hold `create` on namespaces. The gateway does not read Kubernetes on the hot path to
check it.

Nothing the token review already returns binds a token to a run more tightly at no cost, that the gateway can know at create
time: the pod name and uid in the response's `user.extra`, and the service account's uid, belong to a pod and an account that
do not exist yet when the AgentRun is created, and the create response does not carry them. Proposed, not built: the sandbox's
pod name is fixed by the composition (`agent`), so `auth.Workload` could pass `authentication.kubernetes.io/pod-name` on the
principal and the acting rule could require it to be that name, which rules out a token minted for a bare service account
(not a pod); and the sweep's read of the AgentRun (`status`) could one day carry the pod uid to compare.

## The drift guard

`gateway/PORTED.json` lists every Python file the Go gateway ports (26 of them), the Go paths that carry it, what of it
the Go gateway carries, what is left in it for a later slice, and the SHA-256 the file had when the Go code was last
brought level with it. `tests/test_gateway_go.py` fails when a listed file's hash differs. A hash cannot tell whether a
change matters to the port, so the failure asks the author to read it and do one of two things: port the change to Go in
the same pull request (with a test that holds the Go result equal to the Python one), or confirm it does not touch what the
Go gateway carries. Either way the next step is `python tools/gen_gateway_ported.py`, which shows what changed since the
manifest and records the new hashes. The manifest is not edited by hand; its tables live in the tool.

The guard is checked for being empty: the manifest must list a fixed set of core files (removing one to silence a change
fails), every listed file and Go path must exist, and a changed hash is shown to be reported. Every Python file under
`src/autopilot` is also classified, as ported, as belonging to a later slice (`not_ported`, with the slice) or as out of
scope (with the reason), so a new Python module fails the test until someone decides which. The three Clearance pins
(CI, `pyproject.toml`, `go.mod`) are checked to be one release.

Limits: it notices a change to a file, not to a behaviour that lives somewhere it does not list, and it cannot say that a
port is right (the equivalence tests do). Its use is that nobody changes a ported file without having looked at the Go side.

## Timeouts, pools and what never blocks

- Every tool call runs under a context deadline (`GATEWAY_CALL_TIMEOUT_SECONDS`, default 60). The backend sees it and
  returns when it ends; the outcome is still reported, under a fresh bounded context (`error:Timeout`).
- Every backend has its own HTTP client: its own timeout and its own connection pool (`backends/`), so a slow Loki
  cannot starve Prometheus. The Clearance client has its own pool and the outage policy's 250 ms per attempt, one retry
  and a breaker (the client's, unchanged); the model proxy has an upstream pool of its own.
- No process-wide lock. One session's operations are serialized (so a session cannot overspend by racing itself); other
  sessions run in parallel. The model proxy holds a session only for the decision and for the final charge, never while
  a response streams.
- A panic in a backend is an `error:Panic` outcome, not a crash. A failed save of sessions exits the process (crash-only,
  as the Python gateway does); the restart reloads them.

## Authentication

The Go gateway verifies the same three kinds of caller as the Python one (`src/autopilot/engine/auth.py`), chosen by
the token's issuer, behind the same one-minute cache:

| Caller | Verifier | Principal | Set by |
|---|---|---|---|
| a service account of this cluster | the API server's TokenReview | `<namespace>/<name>`, kind `workload` | `AUTOPILOT_RUN_AUDIENCES` (default `autopilot`) |
| a person (Dex in the lab) | the issuer's JWKS: signature, issuer, audience, expiry | `user:<claim>`, kind `user` | `AUTOPILOT_OIDC_ISSUER`, `AUTOPILOT_OIDC_AUDIENCE`, `AUTOPILOT_OIDC_ALLOWED_USERS`, `AUTOPILOT_OIDC_JWKS_URL` (default `<issuer>/keys`), `AUTOPILOT_OIDC_USER_CLAIM` (default `email`) |
| another cluster's service account (Tower's backend) | that cluster's public issuer's JWKS | `<TOWER_CLUSTER>/<namespace>/<name>`, kind `workload` | `TOWER_ISSUER`, `TOWER_CLUSTER`, `TOWER_SERVICE_ACCOUNTS`, `TOWER_JWKS_URL` (default `<issuer>/jwks.json`); the audience is `AUTOPILOT_AUDIENCE` (default `clearance`) |

List only run audiences in `AUTOPILOT_RUN_AUDIENCES`: naming another service's audience there makes that service's local
service-account tokens acceptable as workloads.

The variables, their defaults and their start-up checks are the Python gateway's (an issuer needs its audience and an
allow-list, `TOWER_ISSUER` needs a cluster name and service-account globs, trailing slashes on issuers are removed).
The allow-lists use Python's `fnmatch` rules (`*` matches `/`), reproduced in Go, not `path.Match`. The metadata's
authorization server is the OIDC issuer, else this server. The GitHub Actions verifier of `engine/auth.py` is ported
(`auth.GitHubActions`, with the `repository` attribute and the immutable-id `sub` form) and tested, but `serve` does not
wire it: the Python gateway does not either (since R-3b the core takes GitHub Actions callers, and `CLEARANCE_GITHUB_OIDC_*`
fail its start).

What the verifier accepts, and refuses without saying why (every refusal is the same `token rejected`, nothing from the
token is logged):

- Only `RS256` and `ES256` (the GitHub verifier only `RS256`), each tied to the key's type; never `none`, never HMAC, never
  another algorithm; a token with a `crit` header is refused. The key is picked by `kid`.
- `exp`, `iat`, `iss`, `aud` and `sub` must be present; `exp`, `nbf` and `iat` are checked with 30 seconds of leeway;
  `iss` and `aud` are compared exactly (an `aud` list must hold the audience).
- The routing step reads `iss` without trusting it, only to choose the verifier; a token for an issuer that is not
  configured goes to TokenReview, which refuses it, and a token that is not a JWT is refused.
- A cached success never outlives the token's `exp`; a failure is never cached.
- The JWKS is fetched over https, within 10 seconds, at most 1 MiB, following redirects only on the same host. Plain http
  is allowed for loopback hosts (local runs) and, for any other host, only with `AUTOPILOT_JWKS_ALLOW_HTTP=1` (a Go-only
  setting, off by default): the lab that serves Dex over http turns it on in its render, and `serve` logs a warning naming
  the host at start. Nothing in the code treats a host name such as `.local` as special.
- An unknown `kid` refetches the key set at most once a minute after a successful fetch, however many requests ask, and at
  most once every 5 seconds after a failed one, so a blip at the issuer does not lock sign-in out for a minute. The fetch
  runs detached from the request that triggered it (a caller that names an unknown `kid` and hangs up cannot cancel it);
  callers share it and leave when their own context ends. `serve` fetches each key set once in the background at start;
  a failed first fetch is a warning, not fatal.
- The key set is refetched every 10 minutes whether or not a token asks. A key the issuer removed stays trusted until
  the next refetch (the request that notices the age still uses the old keys), and for as long as the issuer cannot be
  reached: the same as Python, which refetches only for an unknown `kid`.
- Only a token whose signature has verified can start the 10-minute refetch, so an unauthenticated caller cannot drive it. An
  answer with no usable key counts as a failed fetch (the keys held are kept), and after a failure the retry waits 5 s,
  then 10, 20, 40 and at most 60 s, until a fetch succeeds.
- A token may hold only base64url characters and its two dots (anything else, a newline included, is refused before decoding).

Where it differs from Python on purpose (all stricter, or an error handled where Python's escapes):

| Go | Python |
|---|---|
| a token over 16 KiB is refused before parsing | no limit |
| a JWKS URL over plain http is refused at start unless the host is loopback or `AUTOPILOT_JWKS_ALLOW_HTTP=1` | any http(s) URL, any redirect, any size |
| a JWKS key that is not RSA (at least 2048 bits) or P-256 is skipped | one unreadable key makes the whole refresh fail |
| `exp`, `iat`, `nbf` must be JSON numbers | `int()` also accepts a numeric string |
| a failed JWKS fetch, or an `alg` that does not fit the key, is a refusal | raises an error that is not `AuthError` (the server answers 500, not 401) |
| refusals are all one message | the message names the reason (it is not sent to the caller) |

`tests/test_gateway_go_auth.py` feeds the same tokens to both and compares the answer (accepted or refused, principal,
kind, tier ceiling, attributes), and the allow-list globs and the `sub` canonicalisation too; the Go table tests
(`gateway/internal/auth`) cover every refusal above, and a fuzz target (`FuzzTokenParsingAndRouting`) holds that no input
is accepted and none panics.

## How it is proven equal to the Python gateway

1. **The R-3 replay corpus** (Clearance's golden corpus, `testdata/golden/corpus.jsonl`, recorded from the Python
   engine over its whole test suite). `gateway/internal/replay` replays it through the Go gateway's own code against a
   real, unmodified core (with Hangar's bundle, or without it for the lines recorded without the Hangar pack): for every
   line it can take, the evaluation the Go gateway builds equals the Python one field for field, the decision (allow,
   rule, name, message, hint, tier, problems) is identical, the spend leaves the session as the Python one did, the
   grant a `session.open` makes is identical, and the decision record the core writes has the corpus line's fields.
   Against clearance v0.44.0 (the CI pin): 342 tool calls, 261 session opens, 35 session spawns, 49 model calls; 372
   spends, 648 records and 265 grants compared; zero differences. (Before S2: 341 tool calls, 261 opens, 42 model calls,
   329 spends, 605 records, 247 grants; the spawns and the runs acting as their sessions were skipped. The first slice ran
   it against v0.31.0 and v0.35.0.) The 35 spawns go through the real `Gateway.Call` with the real core's grant, so the
   gateway's own check of the grant (`session.AdoptChild`) is shown to accept everything the core makes. Five tool calls are listed as decided differently on purpose since the corpus was recorded: Glidepath's
   contract v2 `propose` class changed the text of the Flight-environment refusals (`decidedDifferentlySince` in
   `replay_test.go`; the corpus is not edited). `TestReplayDetectsDrift` shows a changed field is noticed.
   The corpus is not edited; the lines the replay cannot take are listed below.
2. **The conformance harness** that ships in the Clearance release (`clearance conformance --role runtime`) drives the Go
   gateway's control interface and passes all seven runtime assertions, as it does the Python one
   (`tests/test_gateway_go.py`).
3. **The load test** (`gateway/internal/loadtest`): real MCP `tools/call` requests over HTTP to the real handler, against
   a fake core and backend that each wait a fixed time (2 ms and 1 ms), per call timing of every wait subtracted from the
   request's wall time. At 200 concurrent sessions each calling every ~100 ms, the gateway's own overhead per call
   (excluding the decision, the outcome post and the backend) is p99 under 1 ms in memory, and under 3 ms typically
   with the sessions saved durably to a Postgres on the same laptop. In a closed loop with no think time (12,000 calls a
   second on a machine the load generator, the fake core and the gateway share) the p99 is about 12 ms: that measures
   the machine saturating, not the gateway, and is reported, not asserted.
   `AUTOPILOT_LOADTEST=1 go test -run TestGatewayOverheadPerToolCall ./internal/loadtest` runs it and asserts the 5 ms
   bar; CI runs it in report mode (`AUTOPILOT_LOADTEST=report`) and prints the numbers in the job summary.

### What the replay does not cover (and why)

| Corpus lines | Why |
|---|---|
| nothing now: the 35 `session.spawn` lines and the 8 `tool.call` (1) and `model.call` (7) lines of a run acting as its session, skipped before S2 for want of the run backend, are compared like the others (request, decision, spend, the grant the child is created from, the record) | |
| triggered `session.open` (31) | `open_triggered`, holds and the trigger ledger are not ported |
| `activation` and probe lines (the rest) | the core's own decision engine; they carry no gateway request |
| a request with a number beyond int64 (11 lines) | Python integers are unbounded; the core's types, and so the Go client's, are int64. The core rejects such a request too, so there is nothing to compare |
| one `model.call` with no routes | a gateway with no model routes answers `M006` without asking the core (same in both) |

## What is not carried (after S2)

The Go gateway starts only with what it carries; `serve` refuses to start when the environment asks for something it
does not (`GITHUB_PR_ENABLED`, `AGENT_XRS_ENABLED`, `EVENTS_ENABLED`, `GLIDEPATH_API_URL`, `BACKSTAGE_URL`,
`APP_API_SERVICES`, `ARGO_SYNC_ENABLED`, `AUTOPILOT_EPHEMERAL`), so nobody believes a feature is live when it is not.

Not ported, and still the Python gateway's:

- **The person-facing side of runs (S3)**: `run_agent` as a route (who may run what, holds) and the Preflight routes
  `/v1/preflight/cases` and `/v1/preflight/score`, with the cases, the scoring and the ledger (`preflight.py`). What a person's
  run does once checked is here (`RunAgentAs`, `Candidate`). `Candidate` refuses (`ErrNotCarried`) until a validated parse and
  a fingerprint are supplied: a candidate document is untrusted and the definition schema is S4's, so S3 must not call it
  before S4 or supply both.
- **The human inbox** (`human.request`), person controls (freeze, end, hold, release), the trigger scheduler, `open_triggered`,
  the event bridge, the reconciliation sweep and the trigger ledger (S3). `session_close` here is the owner's tool; Tower's End
  is S3's.
- **Artifacts** (`artifact.put`, `artifact.get`): no handler (S5a); a run's answer is kept as the run path needs it.
- **A candidate's image check is Python's, and too loose to put behind a route** (`Candidate`, TODO in the code): an empty
  `RuntimeImages` allows any registry, and the digest is matched as a substring of the image. S3 must tighten it (the digest
  is `@sha256:` and 64 hex digits at the end of the image; an empty allow-list refuses) before any route calls it.
- **The runtime catalog** (`runtime/catalog.yaml`, `GET /v1/runtimes`, `runtimes.py`): a candidate's image globs are
  `Gateway.RuntimeImages`, which nothing sets yet (S6).
- **Publishing the definition set** to the core (`PUT /v1/definitions`) and the Agent XR loader: the Go gateway reads the
  bundled `agents/` and the pinned set the Python loader keeps in `gateway_definitions`, and publishes nothing. It does
  not validate definitions against the JSON schema (the loader that wrote the set did).
- **Backends**: `metrics.query` and `logs.query` (Prometheus, Loki) are ported with per-backend timeouts and pools. The
  rest (`catalog.read`, `argo.app.get`, `argo.sync.lower`, `app.api.get`, `repo.*`, `xr.request`, `glidepath.*`,
  `airframe.*`, `artifact.*`) have no handler, so a call to them is refused as having no backend, as in a Python
  gateway that does not configure them.
- **`api`** (clearance-api's runtime reads, `api_serve.py`, `read_api.py`, `reads`), Prometheus metrics on `METRICS_PORT`,
  OTLP logs, and a `held` outbox reason (since clearance v0.28.0 the core takes every kind the gateway writes).
- **Release plumbing**: no `gateway-go-v*` tag, image workflow or Apron change. The Python image stays what
  `gateway-image.yaml` builds.

The 7-day canary, moving every definition to it, and removing the Python gateway are the managing agent's later steps,
after the remainder above is ported.

## Running it (locally)

```shell
cd gateway && go build -o autopilot-gateway ./cmd/autopilot-gateway
GATEWAY_DSN=postgresql://... CLEARANCE_CORE_URL=http://clearance-core:8080 \
  CLEARANCE_CORE_TOKEN_FILE=/var/run/secrets/tokens/clearance AUTOPILOT_AGENTS_DIR=../agents ./autopilot-gateway serve
```

It reads the variables the Python gateway reads, for the part it carries: `PORT`, `MODEL_PORT`, `GATEWAY_DSN`,
`CLEARANCE_CORE_URL`, `CLEARANCE_CORE_TOKEN_FILE`, `AUTOPILOT_AGENTS_DIR`, `AUTOPILOT_AUDIENCE`, `MODEL_TOKEN_AUDIENCE`,
`AUTOPILOT_OIDC_ISSUER`, `AUTOPILOT_OIDC_AUDIENCE`, `AUTOPILOT_OIDC_ALLOWED_USERS`, `AUTOPILOT_OIDC_JWKS_URL`, `AUTOPILOT_OIDC_USER_CLAIM`, `TOWER_ISSUER`, `TOWER_CLUSTER`, `TOWER_SERVICE_ACCOUNTS`, `TOWER_JWKS_URL`, `AUTOPILOT_JWKS_ALLOW_HTTP` (Go only),
`AUTOPILOT_RESOURCE_URL`, `AUTOPILOT_EXPIRE_SECONDS`, `GATEWAY_OUTAGE_ALLOW_READS`, `MODEL_ROUTES`, `MODEL_KEY_FILE`,
`AUTOPILOT_RUN_AUDIENCES`, `CLEARANCE_CORE_TIMEOUT`, `PROMETHEUS_URL`, `LOKI_URL`, `LOG_LEVEL`; and three of its own: `GATEWAY_CALL_TIMEOUT_SECONDS` (60),
`MODEL_TIMEOUT_SECONDS` (300), `GATEWAY_PG_CONNS` (16). It takes the gateway database's writer lock, so it cannot run
beside the Python gateway on the same database.

`serve` needs no new variable for runs: the run backend is the in-cluster Kubernetes API (as the Python gateway always uses it),
so the gateway's identity needs the Role on AgentRuns in `autopilot-runs` it already has.

Tests: `cd gateway && go vet ./... && go test -race ./...`. The replay needs a clearance checkout (`CLEARANCE_SRC`) and the
core binary (`CLEARANCE_CORE_BIN`); the database tests need a scratch Postgres (`AUTOPILOT_TEST_PG`); without them those
tests skip. `pytest tests/test_gateway_go.py` runs all of it with the suite's core, and the drift guard.
